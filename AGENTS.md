# AGENTS.md — работа агента в NewscastNavigator

Общайся с владельцем по-русски. Пользовательские тексты пишутся по-русски;
имена в коде соответствуют принятым в проекте соглашениям.

## Начало задачи

1. Проверь каталог, ветку, HEAD и `git status --short --branch`. Сохраняй чужие изменения.
2. Прочитай [текущее состояние](docs/PROJECT_STATE_RU.md).
3. Через [каталог](docs/README_RU.md) выбери основные документы своей задачи.
   Архив читается для конкретного вопроса; весь исторический журнал загружать не нужно.
4. Определи действующие разрешения из текущего разговора. Перед реализацией
   проведи read-only анализ и получи утверждение плана по файлам. В утверждённых
   границах продолжай без повторного согласования каждого шага.

Продуктовые требования: [спецификация](docs/product/SPEC_RU.md), затем
[критерии качества](docs/product/EVAL_RUBRIC_RU.md), утверждённый план и
принятые уточнения владельца. Код — свидетельство реализации. Старые планы,
результаты и разрешения в архиве не являются поручением повторить работу.

## Инварианты и данные

- Production на VDS содержит рабочие данные. Изменения проходят совместимые
  миграции и проверенный backup/recovery; историческое разрешение пересобрать
  прототип не разрешает удалить нынешние данные.
- Один актуальный сценарий; любая разрешённая сохранённая правка сразу актуальна.
  Проверка и корректура — отметки над текстом. Поздняя правка автоматически
  не снимает корректуру; повторную вычитку назначает руководство.
- Сохраняй поведение табличного редактора и CaptionPanels; перед изменением
  закрепляй его characterization-тестами. Не возвращай ручные версии,
  branch/merge, монтажные/титровые копии, общую ленту комментариев и режим v2.
- Соблюдай явные нецели спецификации. Изменение утверждённого продукта согласуется
  с владельцем. Git хранит удалённый код; папку `legacy` не создавай.
- Во время ввода локальное состояние редактора главное. Ответ сервера не
  заменяет редактор целиком, устаревший ответ не затирает свежий ввод.
  ID строк создаются до первого сохранения. Успешное сохранение не меняет
  layout, focus, selection или scroll; ошибка сохраняет локальный текст.
- Тесты и seed используют синтетические данные. Не читай, не печатай и не
  коммить реальные секреты, production `.env`, рабочие сюжеты и контакты.
  Разрешённый внутренний демонабор хранится отдельно от тестовых фикстур.

## Работа и проверки

- Работай в отдельной ветке или worktree; `main` напрямую не меняй.
- Для изменения поведения сначала воспроизведи его тестом. Завершай вертикальные
  checkpoints проверками по риску, удалением заменённых частей и небольшими
  осмысленными локальными коммитами.
- [Инженерные правила](docs/engineering/DEVELOPMENT_RU.md) задают команды.
  Backend: `pytest -q`; frontend: `npm test -- --run`, `npm run build`;
  соответствующий `docker compose ... config`. Для UI нужна фактическая
  browser-проверка. Документы и конфигурации проверяются без запуска приложения.
- Для эксплуатационного изменения: ранний inventory и финальная изолированная
  репетиция; по каждому затронутому deploy/migration/backup/restore/CI/seed/smoke/
  recovery пути указать KEEP, ADAPT, REPLACE или DELETE. Миграция, synthetic seed,
  health, smoke и backup/restore проверяются по риску изменения.
- Канонические среды: localhost для изолированной разработки,
  [домашний LAN-only HTTPS](docs/operations/HOME_TEST_WORKFLOW_RU.md) для приёмки,
  [Hostland](docs/operations/hostland/README.md) для production. Тестовую БД в
  production не переносить.
- Действия на домашнем сервере и VDS требуют разрешения соответствующего этапа.
  Уже данное разрешение действует в своих границах. Push, PR, merge, tag,
  публикация релиза и deploy требуют отдельной команды пользователя.

## Агенты и куратор документации

Координатор: `gpt-6-sol/high`; текст инструкции модель не переключает.
Если выбранная пара отличается или недоступна, сообщи и остановись перед
делегированием; не подменяй её молча. Роли, модели и обязательный ограниченный JSON-контракт —
в [PROJECT_AGENTS_RU.md](docs/engineering/PROJECT_AGENTS_RU.md).

Делегируй только нужную ограниченную подзадачу. Существенное изменение
получает независимые review и verification одного снимка. После правок
повтори затронутые проверки. Доступность роли не расширяет её полномочия.

`documentation-steward` — куратор структуры, навигации и согласованности
документации. Включай его проверку при изменении продукта/эксплуатационного
процесса, реорганизации документов, завершении существенной задачи и подготовке
релиза. Он проверяет документы исполнителя, не заменяя предметное ревью.
Для опечатки достаточно self-review и автоматических проверок.

## Завершение задачи и документация

Следуй [стандарту документации](docs/DOCUMENTATION_POLICY_RU.md).
Обновляй основные документы вместе с изменением. Используй `docs/plans/`
для утверждённой работы и `docs/reports/` для новых доказательств. Закрытый
план переносится в `docs/archive/` со ссылкой на результат. Прежний журнал
в хранилище исторических свидетельств заморожен и не дописывается.

Обнови короткий PROJECT_STATE при смене этапа или точки продолжения.
Проверь `python3 scripts/check_docs.py` и `git diff --check`; в итоговом
сообщении укажи изменения, проверки, удалённое/перенесённое, ограничения и
следующий шаг. Для существенной задачи учти заключение куратора.
