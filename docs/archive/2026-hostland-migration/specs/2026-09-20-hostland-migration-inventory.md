# Hostland: первичное обследование перед переездом

Дата проверки: 20 сентября 2026 года; домашняя площадка около 18:49 UTC,
VDS около 19:16–19:20 UTC.
Статус: обе площадки обследованы в режиме чтения; ключ VDS подтверждён
владельцем через консоль, аутентифицированный SSH-доступ проверен. Это исходные наблюдения для
file-level плана, а не отчёт о завершённом переносе.

## Граница действий

Владелец разрешил начать подготовку и предоставил параметры SSH VDS.
Выполнены только чтение локальных настроек доступа, SSH-команды обследования
домашней площадки и VDS, получение публичного SSH-ключа VDS и DNS-запросы.
Приложение, серверные настройки, DNS, данные и расписания не изменялись.
Новые backup не создавались. Production env, пароли, приватные ключи,
содержимое сюжетов и файлы backup не читались и не выводились.

## HTTPS и DNS

- Рабочий gateway опубликован на LAN-интерфейсе домашнего сервера, порт 8088.
- Внешние 80/443 занимает отдельный edge-контейнер прежнего Compose project.
  HTTPS нельзя считать частью четырёх основных контейнеров нового runtime.
- Также обнаружен старый nginx-контейнер без опубликованных внешних портов.
  Его назначение и необходимость пока не подтверждены; удаление не выполнялось.
- Публичный DNS-ответ указывает NS `ns1.reg.ru` и `ns2.reg.ru`.
- A-запись соответствует домашнему внешнему адресу. Наблюдавшийся TTL около
  21600 секунд (6 часов). Доступ владельца к управлению DNS не проверен.
- Первый запрос AAAA не дал записей. Авторитетное отсутствие AAAA и политика
  CAA ещё не подтверждены: дополнительные запросы дали mismatch/timeout.
  Зависшую локальную DNS-проверку остановили; macOS dig завершился с внутренней
  ошибкой. Это ограничение проверки, а не доказательство неисправности DNS.

## Домашние резервные копии

- В ранее известном каталоге приложения найдена одна dump-копия.
- Размер dump: 285027 bytes; весь найденный каталог около 292 KiB.
- Проверялись метаданные файлов; содержимое, валидность checksum и
  восстанавливаемость этой копии в данном обследовании не проверялись.
- Права dump `0664`, backup-каталога `0775`, но родительский приватный каталог
  имеет `0700`, а домашний каталог пользователя — `0750`.
- Широкие биты самого файла не доказывают доступность другим пользователям:
  закрытый родительский каталог ограничивает проход. Полный ACL-аудит не
  проводился. Для нового механизма планируются явные ограниченные права
  и на каталог, и на каждый файл.
- У прикладного SSH-пользователя crontab не найден; среди видимых системных
  timers backup приложения не найден. Это не исключает root cron, задачи
  другого пользователя или внешнее резервирование.
- Свободного места для текущего объёма достаточно. Выбор выделенного каталога,
  владельца, шифрования, сроков хранения и мониторинга требует точного плана.

## VDS

Адрес, root-login и порт 22 предоставлены владельцем. В локальном known_hosts
для стандартного адреса VDS подтверждённый ключ не найден.

Публичный ED25519 ключ, полученный по сети и независимо подтверждённый
владельцем через консоль Hostland:

`SHA256:PZUa8qLnBx64kgFmDeIzEXDAOn+OYjvSQ7R2FV0KqsI`

Статус ключа: отпечаток совпал с результатом, предоставленным владельцем
из консоли Hostland. Повторный keyscan совпал с подтверждённым значением.
Ключ сохранён только во временный файл known_hosts для строгой проверки
этого подключения; постоянный known_hosts не изменялся.
Команда независимой проверки в консоли:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Пробный SSH-вход существующим ключом проекта при StrictHostKeyChecking=yes
отклонён сервером (publickey,password). У владельца запрошен ввод пароля
непосредственно в локальном Терминале для временного SSH master-соединения.
Новый публичный ключ на VDS не устанавливался. Control socket размещён
в отдельном локальном каталоге с правами 0700; после обследования соединение
нужно закрыть. Пароль не проходит через сообщения или аргументы команды.

Пароль и VNC-токен не сохраняются в этом документе. После ввода пароля
владельцем вход состоялся; выполнены только команды чтения.

Не следует называть меньший MemTotal недопоставкой RAM: подтверждён резерв
512 MiB для crashkernel и накладные расходы ядра. Решение о снятии резерва
и swap принимается отдельно; параметры загрузки сейчас не менялись.

`grub2-common.service` имеет failed с момента загрузки 16 сентября:
`grub-editenv: error: invalid environment block`. Однако текущее чтение
`grub-editenv /boot/grub/grubenv list` успешно и возвращает `recordfail=1`;
`grub-script-check /boot/grub/grub.cfg` проходит. Это исторический сбой службы,
а не доказательство текущей порчи grubenv. Повторный запуск службы, обновления
и проверка перезагрузки ещё не выполнялись. Не пересоздавать grubenv по одному
старому сообщению. Синтаксис `sshd -t` корректен.

В SSH основной конфиг разрешает root; `50-cloud-init.conf` разрешает пароль.
Будущий override должен предшествовать этому файлу и проверяться через
`sshd -T`, включая реальный connection context. Проверка старым master-сокетом
не заменяет новый вход при тестировании изменённых политик.

## Выполнение первого checkpoint — 20 сентября 2026 года

После описанного выше read-only обследования владелец явно утвердил
[план доступа и firewall](../plans/2026-09-20-hostland-initial-hardening.md).
Ниже — новое состояние; исходные наблюдения выше оставлены как baseline.

- Создан `newscast-admin`, uid/gid 1001; публичный ключ проекта установлен
  в authorized_keys. Приватный ключ не передавался на VDS.
- `.ssh` имеет 0700, authorized_keys 0600; владелец newscast-admin.
- `/etc/sudoers.d/newscast-admin` root:root 0440, NOPASSWD: ALL;
  visudo успешно проверил файл и общий конфиг. Это полноценный административный
  ключ, не ограниченный сервисный доступ.
- Новый независимый SSH-вход и `sudo -n true` проверены до и после изменения
  SSH, а также после включения firewall. Во всех проверках multiplexing выключен.
- Установлен `/etc/ssh/sshd_config.d/00-newscast-hardening.conf` из плана.
  Синтаксис и эффективные значения для admin/root проверены до reload.
  PermitRootLogin=no; PasswordAuthentication=no; AuthenticationMethods=publickey;
  AllowUsers=newscast-admin. Прочие ограничения соответствуют плану.
- Новый root-вход отклонён. Password-only проба без передачи пароля отклонена;
  сервер предлагает только publickey. Root password status остаётся P, пароль
  для аварийной консоли не блокировался и не менялся.
- UFW 0.36.2-9build1 и 8 зависимостей установлены из подписанных Ubuntu sources.
  Симуляция и установка: 9 новых пакетов, 0 обновлено, 0 удалено.
  Пакетные списки обновлены; 57 доступных обновлений отложены на следующий этап.
- Firewall активен и включён на загрузку; IPv4 и IPv6 INPUT/FORWARD DROP,
  единственное пользовательское разрешение — TCP/22. Штатные служебные
  исключения UFW сохранены. Исходящие соединения разрешены.
- С Mac TCP/22 доступен; 80/443/5432/8000/8088 дали timeout (3 секунды).
  Это проверенный набор портов, а не полный scan. Global IPv6 отсутствует,
  поэтому внешнего IPv6 теста нет; локальные правила IPv6 проверены.
- Первая проверка IPv6 использовала неверное имя цепочки ufw-user-input.
  После исправления проверки на ufw6-user-input она прошла; настройки
  firewall для этого не менялись.
- grubenv и grub.cfg проверены; grubenv сохранён перед штатным запуском
  grub2-common. Служба завершилась Result=success / ExecMainStatus=0,
  recordfail снят. Failed units: 0. Пересоздание grubenv, grub-install,
  изменение загрузочных параметров и reboot не выполнялись.
- Системные копии находятся на VDS в
  `/root/newscast-bootstrap-backup-iAxQR6WZ`, root:root 0700.
  Это резерв изменённых настроек, а не полный backup приложения.
- Временная root-master-сессия закрыта; после её закрытия независимый
  key-only вход newscast-admin и sudo повторно прошли.
- Код приложения и домашний сервер не менялись; DNS, реальная БД и Docker
  этим checkpoint не затронуты. Никакие данные или старые аккаунты не удалены.

Ключ сервера по-прежнему закреплён в отдельном локальном known_hosts;
текущий путь `/private/tmp/nn-hostland-access-bzl65884/known_hosts` временный.
Он не является единственной записью доверия: публичный fingerprint указан
выше и в плане. После очистки temp-файлов known_hosts потребуется восстановить
со строгой сверкой этого fingerprint. Подготовка постоянного клиентского
профиля доступа включается в следующий эксплуатационный этап.

Остаются: обновления ОС, настройка памяти и логов, проверка перезагрузки,
Docker/HTTPS, домашние полные backup с restore drill и перенос приложения.
Этот checkpoint не означает готовности VDS к production.

## Выводы для дальнейшего плана

1. Объём текущей БД невелик. При отсутствии пользователей обычный dump/restore
   остаётся предпочтительным способом переноса; репликация ради простоя
   не требуется. Время переноса подтверждается репетицией.
2. Домашний сервер доступен по существующему ключу и имеет запас диска;
   повторно запрашивать его SSH-пароль не требуется.
3. Новый VDS должен иметь собственный HTTPS и не зависеть от старого edge.
4. Текущие backup-наблюдения не подтверждают регулярное полное резервирование;
   новый механизм и restore drill обязательны до допуска команды.
5. Низкое текущее потребление RAM контейнерами отражает простой приложения,
   а не доказанную вместимость для будущей нагрузки.
6. Первый checkpoint административного доступа и firewall выполнен.
   Второй этап ОС/Docker также выполнен; далее синтетическая установка,
   HTTPS, полные домашние backup и проверка восстановления.
7. Позднее нужны доступ владельца к DNS и выбор домашнего backup-каталога;
   эти сведения не мешают текущему обследованию VDS.
