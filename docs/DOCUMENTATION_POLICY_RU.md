# Как вести документацию проекта

Документация живёт в Git и изменяется вместе с проектом. [Каталог](README_RU.md)
помогает найти инструкцию; [текущее состояние](PROJECT_STATE_RU.md) позволяет
продолжить работу. Требования к продукту находятся только в [спецификации](product/SPEC_RU.md)
и [критериях качества](product/EVAL_RUBRIC_RU.md).

## Кто отвечает

| Участник | Обязанность |
|---|---|
| Исполнитель изменения | Найти затронутые основные документы, исправить их в том же изменении, проверить ссылки и примеры |
| `documentation-steward` | Проверить размещение, навигацию, согласованность, отсутствие дублей, статус плана и полноту итоговой записи |
| Координатор | Включить документацию в план задачи, учесть замечания куратора и выполнить условия завершения |
| Ревьюер предметной области | Проверить правильность требований, поведения и команд; куратор не заменяет эту проверку |
| Владелец проекта | Принимать изменения продукта и эксплуатационной политики; назначать реальные полномочия |

Куратор вызывается при реорганизации документов, изменении продуктового или
эксплуатационного процесса, завершении существенной задачи и подготовке
релиза. Для исправления опечатки достаточно self-review и автоматических
проверок. Постоянный фоновый агент этим правилом не создаётся.

Контракт вызова и модель — в [правилах делегирования](engineering/PROJECT_AGENTS_RU.md).
Куратор читает только разрешённые источники. Исправления поручаются ему
явно с перечнем файлов; доступность роли не даёт доступа к серверам.

## Где хранить сведения

| Содержание | Основной раздел | Когда обновлять |
|---|---|---|
| Поведение продукта и права | `product/` | При утверждённом изменении требования |
| Действия сотрудника | `guides/` | При изменении доступного рабочего сценария |
| Архитектура, контракты, разработка | `engineering/` | При изменении реализации или инженерного процесса |
| Среды, выпуск, копии и восстановление | `operations/` | При изменении команды, условия или инфраструктурного процесса |
| Причина существенного выбора | `decisions/` | При принятии или замене решения |
| Утверждённая работа | `plans/` | При смене шага и статуса задачи |
| Выполненные проверки и выпуск | `reports/` | После конкретного проверяемого этапа |
| Сохранённые эталоны и нужные закрытые материалы | `archive/` | При закрытии задачи и кураторском отборе |

Одно правило имеет один основной документ. В README компонентов и других
местах оставляют ссылку и краткое объяснение, а не ещё один полный набор
команд. Исторический документ не изменяет текущие требования и разрешения.

## Паспорт и оформление

Каждый управляемый документ docs содержит короткий YAML-паспорт:

```yaml
---
type: runbook
status: active
owner: operations
audience: operators, agents
reviewed: 2026-09-30
---
```

`owner` обозначает ответственную роль, а не автоматически назначенного
сотрудника. `reviewed` — дата содержательной сверки с указанными источниками;
редакционная правка и смена даты не доказывают новый запуск команды или
состояние сервера. Источники и пределы проверки описываются рядом с фактом.

Допустимые типы: `index`, `state`, `policy`, `reference`, `guide`, `runbook`,
`decision`, `plan`, `report`, `historical`, `template`. Статусы: `active`,
`planned`, `in_progress`, `accepted`, `completed`, `historical`, `template`,
`superseded`. Используй [шаблоны](templates/README_RU.md).

Имена действующих документов описывают назначение; планы, решения и отчёты
начинаются с даты `YYYY-MM-DD`. Пиши по-русски, раскрывай необходимые термины,
используй заголовки по смыслу и примеры только с синтетическими данными.
Ссылки внутри репозитория — относительные. Реальные секреты, пользовательские
данные и незашифрованные рабочие копии в документацию не попадают.

## Жизненный цикл задачи

1. До правки определить основные документы по [каталогу](README_RU.md).
   В плане указать их вместе с кодом, конфигурациями и проверками.
2. Обновлять действующие инструкции в том же изменении. Старые противоречащие
   указания заменять, а не дописывать очередное уточнение в конец.
3. Для инструкции описать условия применения, команды/действия, ожидаемый
   результат и действия при ошибке. Историю внедрения вынести в отчёт.
4. В отчёте зафиксировать снимок, проверку, результат и её границы. Старое
   наблюдение `NOT_RUN` не переписывать в `PASS` без новой проверки.
5. Закрыть план: поставить `completed`, указать итоговый отчёт, перенести в
   `archive/<год>-<тема>/` и обновить ссылки. В `plans/` остаётся только будущая
   или выполняемая работа. Отменённый план архивировать с объяснением решения.
   При последующем отборе завершённый план можно удалить из дерева, если его
   содержание покрыто результатом/решением; сохранить исходный Git SHA и путь.
6. Обновить PROJECT_STATE, если изменились текущий этап, препятствие или маршрут
   продолжения. Он содержит до 100 строк и не накапливает хронику.
7. Для задачи с коммитами получить Git-заключение `repository-steward` и указать
   достигнутые этапы по [Git workflow](engineering/GIT_WORKFLOW_RU.md).
8. Получить проверку куратора для существенной задачи; замечания исправить или
   явно разрешить с доказательством. Заполнить пункт документации в PR/итоге.

Закрытая историческая задача не открывается заново из-за старого TODO.
Новая работа появляется из текущего поручения или нового подтверждённого
наблюдения. Условия будущего rollback и границы испытаний остаются в
профильных инструкциях как условия применения.

## Проверки и защита от накопления ошибок

Из корня проекта:

```bash
python3 -m unittest discover -s scripts/tests -p 'test_check_docs.py'
python3 scripts/check_docs.py
git diff --check
```

CI выполняет те же структурные проверки: обязательные входы, паспорта,
внутренние ссылки и заголовки, достижимость действующих документов из каталога,
корректность расположения планов. Отобранные архивные Markdown тоже проходят
проверку паспорта, ссылок и достижимости. Манифесты визуальных эталонов
проверяются по tracked составу, размерам и SHA-256. Цель ссылки должна входить в Git; локальный
ignored-файл не делает её доступной остальным читателям.

Проверка смысла остаётся у автора, куратора и предметного ревьюера. Куратор
перед релизом также просматривает активные планы и документы затронутых
областей. Возраст файла сам по себе не означает ошибку или выполненную проверку.
Внешние ссылки и серверы автоматически этой проверкой не опрашиваются.

## История и доказательства

Архив хранит материалы с конкретным дальнейшим применением: утверждённый
визуальный эталон, основание действующего решения/отчёта или вход проверки.
Промежуточные варианты, старые промпты, дубли и завершённые подробные планы
можно удалить из текущего дерева после переноса полезного содержания.
Отчёт отбора фиксирует точный исходный Git SHA, путь, причину и хеш; историю
репозитория не переписывают. Куратор проверяет сохранность уникальных сведений,
входящие ссылки и программные зависимости до удаления.

Исторические machine-readable доказательства проверяются по хешам либо
в checkout, либо как Git blobs точного commit — это указано в
[манифесте и каталоге](archive/README_RU.md). Старые результаты не получают
новый PASS от редакционного переноса. Проверкам Git blobs нужна полная
локальная история; CI использует `fetch-depth: 0`. Новые записи в прежний
PROGRESS не добавляют.

Локальный ignored-файл не признаётся мусором автоматически. Можно удалять
подтверждённо устаревшие временные материалы инструментов, воспроизводимые
кеши и пустые остаточные каталоги. Рабочие БД, backups, секреты, зависимости,
неизвестные и уникальные пользовательские файлы требуют отдельного основания.
Перед очисткой проверяют происхождение, ссылки, активное использование и
границы путей; символические ссылки не обходят. Общий `git clean -fdx` не используют.
