# NewscastNavigator Product Reset — критерии готовности

Статус: утверждено владельцем продукта 10 июля 2026 года.

## 1. Правило завершения

Product Reset считается готовым только при одновременном выполнении четырёх условий:

1. Все обязательные deterministic-проверки пройдены.
2. UX/UI набрал не менее 90 из 100 баллов.
3. Ни одна отдельная UX-категория не получила менее 8 из 10.
4. В runtime и пользовательском интерфейсе не осталось заменённых legacy-механизмов.

Успешная сборка сама по себе не является завершением.

## 2. Проверочная среда

Автоматические проверки используют синтетический набор:

- не менее 30 активных сюжетов;
- сюжеты на каждом этапе процесса;
- стандартный и высокий приоритеты;
- не менее 5 архивных сюжетов;
- начальник;
- шеф-редактор и автор;
- корреспондент;
- корректор и автор;
- монтажёр;
- дизайнер;
- оператор.

У пользователей есть имена, должности и функции, но нет фамилий и реальных контактов.

Интерфейс проверяется в Chromium при масштабе 100%:

- 1366 × 768;
- 1920 × 1080.

Мобильные размеры не входят в критерии.

## 3. Обязательные функциональные сценарии

### 3.1. Карточка и доступ

- Автор создаёт сюжет с названием, рубрикой и одним автором.
- Дата фиксируется автоматически.
- Приоритет по умолчанию — `Стандарт`.
- Любой пользователь видит сюжет в общем списке.
- Любой пользователь может открыть и изменить активный сценарий.
- Любой пользователь может добавить путь к материалам.
- Только руководство меняет автора, приоритет и назначения.
- Архивный сюжет доступен только для чтения.

### 3.2. Комбинированные функции

- Автор-начальник не получает запрос на проверку самому себе.
- Автор-шеф закрывает редакционную проверку и направляет текст только корректору.
- Автор-корректор закрывает корректуру, но руководство получает запрос на редакционное подтверждение.
- Пользователь с несколькими функциями видит одну объединённую очередь действий.

### 3.3. Редакционный процесс

- Корреспондент нажимает «Отправить на проверку».
- Начальник или шеф подтверждает редакционную готовность.
- Корректор отмечает текст вычитанным.
- Изменение после корректуры не создаёт копию и не снимает отметку автоматически.
- Шеф получает одно сгруппированное уведомление.
- Повторная корректура запускается только решением руководства.

### 3.4. Производство

- Монтажёр может начать работу до завершения проверки текста.
- Монтажёр получает актуальный сценарий и отмечает «Ролик готов».
- Руководство возвращает правки или отмечает «Ролик готов к титрам».
- Первоначальный допуск к титрам невозможен без редакционной проверки и корректуры.
- Дизайнер получает самый свежий текст.
- Дизайнер отмечает «Титры готовы».
- Изменение текста после начала титрования не блокирует дизайнера.
- CaptionPanels при открытии получает актуальный сценарий.
- После уже выполненной загрузки в CaptionPanels дизайнер получает уведомление, но After Effects не обновляется автоматически.

### 3.5. Пакеты правок

- Внутреннее замечание создаёт пакет с одной областью.
- Внешнее замечание может создать несколько областей с разными исполнителями.
- Каждый исполнитель видит своё действие на главной.
- В карточке весь пакет виден всем.
- Последняя выполненная часть переводит пакет на общий просмотр руководства.
- «Правки выполнены — ролик готов» и «Правки выполнены — титры готовы» не требуют второго действия.
- Цикл внешнего согласования повторяется без создания параллельной системы задач.

### 3.6. Завершение

- Руководство вручную отмечает «Сдано / вышло в эфир».
- Отметка не блокирует правки.
- Архивирование доступно только после неё.
- Архив делает карточку read-only.
- Руководство может вернуть сюжет из архива.

## 4. Автосохранение — hard gate

Тестовая матрица покрывает:

- существующую и новую строку;
- все поддерживаемые типы блоков редактора;
- остановку ввода и продолжение ввода во время запроса;
- нормальный, задержанный и ошибочный ответ;
- потерю и восстановление связи;
- устаревший ответ;
- конфликт серверной редакции.

Обязательные результаты:

- текст никогда не исчезает визуально;
- устаревший ответ не заменяет свежий ввод;
- после перезагрузки присутствует последний подтверждённый текст;
- новая строка не перемонтируется после первого ответа сервера;
- курсор и выделение сохраняются;
- активный элемент не меняется;
- положение прокрутки не меняется;
- смещение редактора при сохранении не превышает 1 пикселя;
- обычное успешное сохранение не показывает мигающий статус;
- при сохранении быстрее двух секунд индикатор не появляется;
- медленное сохранение использует элемент фиксированного размера;
- при ошибке текст остаётся на экране и во временном локальном хранилище;
- после восстановления связи выполняется повторная отправка;
- уход со страницы с неподтверждёнными изменениями вызывает предупреждение.

Автосохранение не должно запускать полную повторную загрузку сюжета.

## 5. Одновременное редактирование

- Первый активный редактор получает временную edit-lease.
- Второй пользователь продолжает читать сценарий.
- Второй пользователь видит имя текущего редактора.
- Второй пользователь не может случайно перезаписать текст.
- Lease снимается после ухода или бездействия.
- Истёкшая lease не остаётся навсегда.
- Серверная редакция защищает от редкого конфликта.
- При конфликте локальный текст не теряется.

## 6. История и восстановление

- История группирует изменения по сеансам, а не по каждому автосохранению.
- Указаны пользователь, время и diff.
- Значимые workflow-действия присутствуют.
- Техническая доставка уведомлений отсутствует в пользовательской истории.
- Восстановить весь сценарий могут только начальник и шеф.
- Восстановление создаёт новую актуальную редакцию.
- Последующие записи истории не удаляются.

## 7. Уведомления

- Автосохранение не создаёт уведомлений.
- Повторные изменения одного сюжета объединяются.
- Пользователь не получает назначение самому себе.
- Монтажёр и дизайнер получают diff с последней открытой редакцией.
- Открытие обновлённого сценария считается ознакомлением.
- Руководство не получает сообщение о каждой обычной правке.
- Уведомление ведёт к нужному сюжету, вкладке и действию.
- Прочитанные сообщения не загромождают очередь.

## 8. Главный экран

На размере 1366 × 768:

- общий список виден сразу;
- таблица начинается в верхней части рабочего пространства;
- одновременно видны не менее шести строк;
- «Требует внимания» не вытесняет таблицу;
- при отсутствии действий этот блок не занимает место;
- отсутствует горизонтальная прокрутка;
- технические коды не видны;
- высокий приоритет различим без аварийного оформления;
- личные действия выделены, но не скрывают общую картину.

В таблице не больше согласованных колонок: приоритет, название, рубрика, автор, текущая ситуация и исполнители.

## 9. Карточка сюжета

- Верхняя область содержит только основные метаданные и текущее действие.
- Есть ровно три вкладки: «Сценарий», «Производство», «История».
- Уведомление открывает правильную вкладку.
- Обновление страницы сохраняет сюжет и вкладку.
- Завершённые этапы не занимают основное пространство.
- Недоступные действия скрыты, а не заменены поясняющими панелями.
- В одном контексте визуально выделено только одно главное действие.
- Нет длинной страницы из независимых рабочих панелей.

## 10. UX/UI score — 100 баллов

Каждая категория получает от 0 до 10 баллов с письменным обоснованием и ссылкой на проверенный экран.

| Категория | Что оценивается |
|---|---|
| Общая иерархия | С первого взгляда понятно, где находится пользователь |
| Фокус на списке | Все активные сюжеты остаются главным объектом |
| Следующее действие | Понятно, что требуется сделать сейчас |
| Плотность | Много рабочих данных без нагромождения |
| Простота | Нет лишних фильтров, бейджей, панелей и повторов |
| Дизайн-код | Узнаётся «Редакционный эфир», а не типовая CRM |
| Согласованность | Одинаковые действия выглядят и работают одинаково |
| Обратная связь | Ошибки понятны, обычные операции ненавязчивы |
| Типографика и доступность | Читаемость, контраст, фокус и клавиатура |
| Общее качество | Интерфейс выглядит готовым рабочим продуктом |

Порог:

- сумма не ниже 90;
- каждая категория не ниже 8;
- оценка сопровождается конкретными недостатками;
- Codex осматривает снимки экранов, а не только код;
- после визуальной итерации сравниваются предыдущий и новый результат.

Самооценка Goal не заменяет финальную проверку Павлом Курзыкиным перед публикацией.

## 11. Доступность

На главном экране, в карточке, формах и уведомлениях:

- нет критических и серьёзных ошибок автоматической accessibility-проверки;
- основной процесс доступен с клавиатуры;
- фокус виден;
- смысл не передаётся только цветом;
- интерактивные элементы имеют доступные названия;
- контраст соответствует WCAG AA;
- modal удерживает и возвращает фокус;
- ошибка объясняет проблему и следующее действие.

## 12. Legacy-gate

В runtime, API, активной схеме, пользовательских текстах и актуальной документации отсутствуют:

- ручные версии текста;
- «сделать текущей»;
- branch/merge;
- отдельные рабочие копии монтажа и титров;
- универсальные выпадающие статусы;
- общая лента комментариев;
- старый режим создания материалов;
- скрытый пользовательский интерфейс v2;
- совместимость со старой схемой;
- неиспользуемые recovery-скрипты.

Точный denylist старых identifiers создаётся предварительным `/plan`. Простого скрытия CSS недостаточно.

## 13. Качество кода

- Ни один крупный UI-компонент не управляет одновременно редактором, производством, уведомлениями и историей.
- Бизнес-переходы проверяются сервером.
- API выражает конкретные действия, а не произвольную установку статуса.
- Не возникает второй источник состояния сценария.
- Новое поведение начинается с теста.
- Новая production-зависимость имеет обоснование.
- Ошибки не подавляются пустыми `catch`.
- Закомментированный legacy отсутствует.
- После каждого checkpoint проходит полный доступный тестовый набор.

## 14. Эксплуатационный код

- Каждый скрипт имеет решение `KEEP`, `ADAPT`, `REPLACE` или `DELETE`.
- Есть один канонический локальный запуск.
- Есть один канонический демонстрационный deploy.
- Fresh build выполняется без старого кэша.
- Пустая PostgreSQL создаётся новой миграцией.
- Синтетический demo-seed применяется.
- Health и smoke проходят.
- Backup создаётся.
- Backup восстанавливается в пустую базу.
- После restore совпадают ключевые данные и повторный smoke проходит.
- Реальные секреты не выводятся.
- `.env.example` содержит обязательные переменные.
- Контейнеры не имеют необоснованно широких привилегий.
- Логи запуска не содержат необработанных ошибок.

## 15. Документация, авторство и демоданные

- Документация описывает фактическую систему.
- Противоречащие старые документы удалены или переписаны.
- Указан разработчик Павел Курзыкин.
- Присутствует уведомление `© 2026 Павел Курзыкин. Все права защищены.`
- Лицензии сторонних зависимостей перечислены.
- Codex не создаёт юридический договор от имени компании.
- Автоматический demo-seed не содержит реальных данных коллег.
- Во внутреннем демонстрационном контуре фамилии коллег удалены.
- Реальные пути к материалам отсутствуют.
- Используются только завершённые сюжеты, разрешённые для показа.

## 16. Машиночитаемый результат итерации

После каждого полного eval сохраняет минимум:

```json
{
  "commit": "local commit sha",
  "checkpoint": "checkpoint name",
  "hard_gates_passed": false,
  "failed_gates": [],
  "ux_total": 0,
  "ux_categories": {},
  "legacy_findings": [],
  "operations_findings": [],
  "largest_remaining_risk": "",
  "next_action": ""
}
```

Конкретный путь и команда eval фиксируются в file-level implementation plan после read-only анализа репозитория.

## 17. Условие остановки Goal

Goal продолжает работу, если:

- не прошёл хотя бы один hard gate;
- UX набрал меньше 90;
- отдельная категория получила меньше 8;
- найден старый параллельный механизм;
- clean deploy или restore не прошли;
- интерфейс не был проверен визуально.

Goal ставится на паузу только при блокирующем продуктовом противоречии, необходимости внешнего разрешения или риске для реальных данных.

Push, PR, merge и deploy не входят в условие завершения и выполняются только после отдельного разрешения владельца.
