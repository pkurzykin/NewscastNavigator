# Управление сотрудниками и обязательная смена временного пароля

Статус: техническая коррекция утверждённой Product Reset модели от 29 июля
2026 года, дополненная утверждённым патчем `1.0.1` от 30 июля 2026 года.

Дополнительный release-контракт и точные ограничения удаления заданы в
`V1_0_1_USER_MANAGEMENT_AND_RELEASE_DESIGN_RU.md`.

## 1. Причина коррекции

В утверждённой модели начальник имеет полный контроль, включая пользователей,
а сотрудник может совмещать несколько функций. Backend уже умеет создавать,
изменять и деактивировать пользователей и выдавать временный пароль, но в
frontend осталась заглушка без списка и операций. Кроме того, требование смены
временного пароля реализовано только экраном frontend: прямой запрос к domain
API после входа пока может обойти этот экран.

Коррекция закрывает это расхождение. Она не добавляет новую роль, второй
пользовательский контур или новую продуктовую сущность.

## 2. Пользовательская модель

- У пользователя остаются логин, отображаемое имя, должность и один или
  несколько кодов функций.
- Управлять сотрудниками может только пользователь с функцией `chief`.
- Начальник видит активных и отключённых сотрудников в одном компактном списке.
- Начальник может:
  - создать сотрудника с временным паролем;
  - изменить логин, отображаемое имя, должность и набор функций;
  - отключить или снова активировать учётную запись;
  - назначить новый временный пароль;
  - полностью удалить ошибочно созданную учётную запись, если сотрудник ещё не
    участвовал в работе и не имеет доменных или исторических ссылок.
- Логин после создания меняет только начальник; логин остаётся уникальным.
- Пароль никогда не возвращается API и не показывается после отправки формы.
- Нельзя отключить или лишить функции `chief` последнего активного начальника.
- Нельзя удалить себя, последнего активного начальника или сотрудника,
  участвовавшего в работе. Для такого сотрудника используется отключение.

## 3. Временный пароль

- Созданная учётная запись и учётная запись после сброса пароля получают
  `must_change_password=true`.
- Вход с временным паролем разрешён, чтобы пользователь мог открыть форму его
  смены.
- До успешной смены пароля доступны только:
  - `POST /api/v1/auth/login`;
  - `GET /api/v1/auth/me`;
  - `POST /api/v1/auth/change-password`;
  - `POST /api/v1/auth/logout`.
- Любой другой API-запрос получает `403 PASSWORD_CHANGE_REQUIRED`.
- После успешной смены пароля флаг снимается и обычный доступ восстанавливается.
- Существующий production-admin переносится с текущим password hash и
  `must_change_password=false`; его действующий пароль не меняется.

## 4. Read model и API

Добавляется chief-only read model:

`GET /api/v1/admin/users`

Ответ:

```json
{
  "items": [
    {
      "id": 1,
      "username": "admin",
      "display_name": "Администратор",
      "position": "Начальник",
      "function_codes": ["chief"],
      "is_active": true,
      "must_change_password": false,
      "created_at": "2026-07-29T12:00:00Z",
      "updated_at": "2026-07-29T12:00:00Z"
    }
  ],
  "function_options": [
    {"code": "chief", "label": "Начальник"},
    {"code": "chief_editor", "label": "Шеф-редактор"},
    {"code": "author", "label": "Автор"},
    {"code": "proofreader", "label": "Корректор"},
    {"code": "video_editor", "label": "Монтажёр"},
    {"code": "designer", "label": "Дизайнер титров"},
    {"code": "operator", "label": "Оператор"}
  ]
}
```

Существующие command endpoints сохраняются:

- `POST /api/v1/admin/users`;
- `PATCH /api/v1/admin/users/{id}`;
- `POST /api/v1/admin/users/{id}/reset-password`.

Патч `1.0.1` расширяет `PATCH` необязательным `username` и добавляет
`DELETE /api/v1/admin/users/{id}` только для безопасного удаления
неиспользованной учётной записи.

После успешной команды frontend заново получает read model. Backend остаётся
единственным источником прав, допустимых функций, password policy и инварианта
последнего начальника.

## 5. Интерфейс

- Страница `/admin` получает заголовок, кнопку «Добавить сотрудника» и таблицу.
- Таблица показывает имя, логин, должность, функции, состояние учётной записи и
  состояние пароля.
- Отключённые сотрудники остаются видимыми и явно помечены.
- Создание и изменение выполняются в компактных modal/dialog формах; edit
  dialog также содержит поле логина.
- Набор функций выбирается чекбоксами из `function_options` сервера.
- Отключение требует подтверждения.
- Сброс пароля требует ввода нового временного пароля дважды.
- Удаление требует отдельного подтверждения с именем и логином; серверный отказ
  предлагает отключить использованную учётную запись.
- После успешной команды password inputs очищаются; значение не попадает в
  toast, DOM списка, URL, историю или логи.
- Ошибка остаётся рядом с формой и не стирает непарольные поля.

## 6. Проверки

- Backend API: chief-only список, сортировка активных выше отключённых, отсутствие
  password hash, команды и инвариант последнего начальника.
- Backend auth: пользователь с временным паролем видит `/auth/me`, меняет пароль,
  но до смены получает `PASSWORD_CHANGE_REQUIRED` на domain и admin endpoints.
- Frontend component: список, создание, изменение логина и функций,
  подтверждение отключения и удаления, повторная активация, сброс пароля,
  очистка password fields и отображение серверной ошибки.
- Browser: начальник проходит полный CRUD-срез, включая удаление
  неиспользованного сотрудника и отказ для использованного; обычному
  пользователю раздел не виден; временный пользователь не попадает в AppShell
  до смены пароля.
- Accessibility: формы имеют labels, dialogs имеют доступные имена, status и
  alert объявляются семантически.

## 7. Вне рамок

- Самостоятельная регистрация и восстановление пароля по email.
- Email, телефон, фамилия, контакты и внешняя identity-система.
- Удаление использованных пользователей, каскадное удаление или анонимизация
  исторических ссылок.
- Переключатель одной «текущей роли».
- Массовые операции, импорт сотрудников и журнал просмотра паролей.
