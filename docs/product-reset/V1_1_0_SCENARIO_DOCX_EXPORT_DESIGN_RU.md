# NewscastNavigator 1.1.0 — шапка сценария и экспорт DOCX

Статус: утверждено владельцем продукта 6 августа 2026 года.

## 1. Назначение

Этот документ задаёт следующую обратно совместимую возможность после релиза
`1.0.2`:

- длинное название в синей шапке редактора переносится и остаётся полностью
  видимым;
- рядом с названием и рубрикой хранится свободный хронометраж;
- актуальный сценарий выгружается в редактируемый DOCX, пригодный для обычной
  редакционной работы в Word.

Изменение не возвращает удалённую до Product Reset модель ручных версий. В
продукте по-прежнему существует один актуальный сценарий, а технический номер
редакции используется только для защиты от конфликтов.

## 2. Основание и границы изменения Product Reset

Первоначальный `IMPLEMENTATION_PLAN_RU.md` предписывал удалить старый экспорт
DOCX/PDF вместе с монолитным legacy-контуром. Это решение было выполнено и не
отменяется: старый endpoint, старые шаблоны и старый UI не восстанавливаются.

Экспорт из этого документа — новая каноническая функция единственного
актуального сценария. При реализации `SPEC_RU.md`, `EVAL_RUBRIC_RU.md` и
`IMPLEMENTATION_PLAN_RU.md` получают короткую согласованную поправку,
объясняющую это различие.

Вне рамок:

- экспорт PDF;
- выбор редакции или состояния текста для экспорта;
- архив экспортов, история скачиваний и серверное хранение DOCX;
- загрузка или настройка Word-шаблонов пользователем;
- встраивание файлов шрифтов в DOCX;
- изменение шапки формы создания сюжета или колонок общего реестра;
- импорт DOCX обратно в сценарий;
- восстановление удалённого legacy-кода;
- отдельный интерфейс или API `v2`;
- изменение контрактов CaptionPanels.

## 3. Источники макета

Проанализированы два предоставленных владельцем продукта DOCX за пределами
репозитория. Они остаются только референсами и не копируются в Git, тестовые
фикстуры или контейнерные образы. В репозитории не сохраняются реальные
названия сюжетов, фамилии, тексты и производственные данные из этих файлов.

Из референсов принят общий формат:

- A4, книжная ориентация;
- одна редактируемая таблица;
- синие объединённые строки метаданных сверху;
- три рабочие колонки: «Текст в титре», «В кадре», «Звук»;
- перенос текста, разная гарнитура, жирный, курсив, зачёркивание и цветовая
  заливка фрагментов.

Референсы различаются полями страницы, пропорциями колонок, оттенком синего и
гарнитурами. Поэтому бинарный файл не объявляется скрытым шаблоном. Ниже
зафиксирован один воспроизводимый макет.

## 4. Метаданные сюжета

### 4.1. Новое поле

В `stories` добавляется nullable-поле `duration_text`:

- тип — строка длиной до 64 символов;
- пользователь вводит свободный текст, например `04:00`, `3:30–4:00` или
  `до 5 минут`;
- пробелы по краям удаляются;
- пустое значение сохраняется как `NULL`;
- существующие сюжеты после миграции имеют `NULL`;
- формат времени не вычисляется и не валидируется как таймкод.

Изменение хронометража считается содержательным изменением метаданных сюжета:
обновляет `stories.updated_at` и создаёт обычное понятное событие истории
метаданных. Техническая редакция сценария из-за этого не увеличивается.

### 4.2. Права

Хронометраж изменяют те же пользователи, что название и рубрику: автор сюжета
или руководство. Backend остаётся источником разрешения. Остальные видят
значение без возможности правки.

Любой зарегистрированный пользователь, которому доступна карточка, может
скачать DOCX активного или архивного сюжета. Архивная карточка остаётся только
для чтения, но экспорт доступен.

## 5. Синяя шапка редактора

Шапка содержит три подписанных поля в порядке:

1. «Название».
2. «Рубрика».
3. «Хронометраж».

Название остаётся одной логической строкой данных, но отображается через
автоматически растущее многострочное поле:

- короткое название занимает одну строку;
- длинное переносится по словам и увеличивает высоту поля и синей шапки;
- `Enter` не создаёт перевод строки в названии;
- переводы строк из вставленного текста нормализуются в пробелы;
- лимит названия остаётся 255 символов;
- изменение высоты не сбрасывает focus, selection или scroll редактора.

На согласованных desktop-ширинах три поля располагаются в одной строке. При
недостаточной ширине они переносятся целыми блоками, без горизонтальной
прокрутки и наложения подписей.

Хронометраж включается в тот же metadata save coordinator, что название и
рубрика. Координатор сохраняет только последнюю локальную редакцию, не заменяет
открытый ввод полным ответом сервера и не позволяет устаревшему ответу
перезаписать более новое значение.

## 6. Пользовательский поток экспорта

В существующей липкой панели инструментов появляется кнопка «Экспорт DOCX».
Панель и кнопка остаются под рукой при вертикальной прокрутке. Для архивного
сюжета кнопка также видима, хотя редактирование отключено.

Для активного сюжета одно нажатие выполняет fail-closed последовательность:

1. Редактор фиксирует текущее содержимое всех открытых rich-text полей в
   локальной модели.
2. Немедленно запускаются отложенные сохранения строк и метаданных, включая
   название, рубрику и хронометраж.
3. Клиент ждёт подтверждения обоих сохранений.
4. Только после подтверждения клиент запрашивает DOCX с ожидаемыми номером
   редакции и значениями метаданных.
5. Backend сравнивает ожидания с каноническим состоянием и создаёт документ из
   одного согласованного снимка БД.
6. Успешный ответ передаётся браузеру как файл.

Для архивного сюжета шаги сохранения пропускаются: экспортируется неизменяемый
канонический снимок, уже загруженный и подтверждённый сервером.

Во время операции кнопка заблокирована и имеет текст
«Подготавливаем DOCX…». Повторное нажатие не создаёт второй запрос.

Если сохранение, lease, авторизация, сеть или проверка снимка завершаются
ошибкой, скачивание не начинается. Локальный текст остаётся в редакторе, а
пользователь получает конкретное русское сообщение и может повторить действие.
Старый или частично сохранённый документ никогда не выдаётся как успешный.

После успешного ответа применяется обычное поведение браузера:

- если браузер настроен спрашивать место сохранения, пользователь выбирает
  папку;
- иначе файл появляется в стандартной папке загрузок;
- отдельной второй кнопки «Скачать» нет.

## 7. API и согласованность снимка

Новый endpoint:

`POST /api/v1/stories/{story_id}/scenario/export-docx`

Тело запроса содержит:

- `expected_revision: int`;
- `expected_title: str`;
- `expected_rubric_id: int | null`;
- `expected_duration_text: str | null`.

Endpoint требует обычную сессионную cookie и не вводит отдельную схему
авторизации. Он в одной транзакции читает сюжет, рубрику, сценарий и его строки,
проверяет ожидаемые значения и строит неизменяемый внутренний снимок. При
расхождении возвращается `409 EXPORT_SNAPSHOT_MISMATCH`; клиент предлагает
обновить карточку, но не подменяет локальный ввод.

Успешный ответ:

- `Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document`;
- `Content-Disposition: attachment` с безопасным ASCII fallback и UTF-8
  `filename*`;
- `Cache-Control: no-store`;
- тело — байты DOCX.

Имя файла строится из текущего названия. Запрещённые для распространённых
файловых систем символы, управляющие символы и последовательности пути
заменяются; завершающие точки и пробелы удаляются; длина основы ограничивается.
Если после очистки имя пустое, используется `Сценарий-<story_id>.docx`.

Экспорт не изменяет `updated_at`, номер редакции, историю, workflow,
production state или уведомления.

## 8. Генерация DOCX

### 8.1. Технический подход

DOCX создаётся на backend библиотекой `python-docx`. Для возможностей, которых
нет в её публичном API, разрешены небольшие изолированные помощники OOXML.
Библиотека фиксируется в lock/dependency metadata и проходит проверку лицензии
и чистую контейнерную установку.

Генератор принимает только неизменяемый снимок и возвращает `BytesIO`. В
обычном и ошибочном путях запрещены:

- временные DOCX на файловой системе;
- копии в application storage;
- архив экспортов;
- фоновые задачи очистки файлов.

### 8.2. Страница и таблица

Канонический макет:

- A4, книжная ориентация;
- поля: слева 3 см, справа 1,5 см, сверху 2 см, снизу 2 см;
- одна таблица шириной 17,49 см;
- ширины рабочих колонок: 9,68 см / 5,26 см / 2,55 см;
- оттенок синих строк метаданных и заголовков: `#B6DDE8`;
- чёрные границы 0,5 pt;
- вертикальное выравнивание рабочих ячеек сверху;
- высота строк не фиксируется: Word свободно переносит длинный текст и делит
  таблицу по страницам.

В начале таблицы идут три отдельные объединённые на всю ширину строки:

1. актуальное название;
2. актуальная рубрика;
3. `Хронометраж <значение>` или `Хронометраж —`, если значение не задано.

После них идёт синяя строка заголовков «Текст в титре», «В кадре», «Звук».
Базовая гарнитура документа — `PT Sans`, базовый размер рабочего текста —
12 pt. Имена шрифтов записываются в DOCX, но файлы шрифтов не встраиваются:
фактический вид на другом компьютере зависит от установленных там гарнитур.

### 8.3. Отображение строк сценария

Каждая строка редактора создаёт ровно одну рабочую строку Word в исходном
порядке. Тип блока не выводится отдельной колонкой.

«Текст в титре»:

- `podvodka` — основной текст;
- `zk` — основной текст;
- `zk_geo` — геопривязка отдельным абзацем, затем основной текст;
- `snh` — ФИО, должность и основной текст отдельными абзацами;
- `life` — пусто.

«В кадре» для любого типа блока:

- все пары «имя файла / TC» в порядке редактора, каждая отдельной группой
  строк;
- TC выводится как введённый диапазон `tc_in`–`tc_out`; существующая логика
  нескольких файлов сохраняется;
- затем отдельным абзацем выводится содержимое текущего поля «В кадре», если оно
  заполнено.

«Звук»:

- для `life` — основной текст блока;
- для остальных типов — пусто.

Пустые значения не создают служебные подписи или прочерки внутри рабочих
строк. Переводы строк пользователя сохраняются.

### 8.4. Форматирование

Для целей `text`, `geo`, `speaker_fio` и `speaker_position` генератор читает
сохранённый TipTap JSON из `rich_text`. Поддерживается ровно существующий набор
редактора:

- гарнитура;
- жирный;
- курсив;
- зачёркивание;
- цветовая заливка;
- абзацы и ручные переводы строк.

Форматирование применяется на уровне Word runs, поэтому разные фрагменты одной
ячейки сохраняют разные свойства. `formatting.targets` задаёт внешний вид по
умолчанию для цели; marks конкретного rich-text фрагмента имеют приоритет.

Разрешены только гарнитуры и цвета из текущих списков редактора. Неизвестная
гарнитура заменяется на `PT Sans`, некорректный цвет — на отсутствие заливки.
Ссылки, изображения, списки, произвольный HTML, внешние стили и неподдержанные
TipTap nodes не переносятся. Их видимый текст сохраняется безопасно; скрипты и
OOXML из пользовательского ввода не интерпретируются.

Служебные core properties DOCX не содержат имя локального пользователя,
рабочие пути, исходные имена референсов, временные каталоги или серверные
данные. Комментарии и tracked changes не создаются.

## 9. Компоненты и границы ответственности

Изменение разделяется на узкие части:

- модель и migration хранят `duration_text`;
- существующая metadata command валидирует права, нормализует значение и
  создаёт историю;
- metadata header отвечает только за три поля и визуальный перенос;
- frontend export coordinator отвечает за flush, ожидание подтверждений и
  скачивание;
- backend snapshot builder отвечает за согласованное каноническое чтение;
- чистый DOCX renderer отвечает только за преобразование снимка в OOXML;
- API route отвечает за авторизацию, HTTP-контракт и безопасное имя файла.

DOCX renderer не обращается к БД, файловой системе, текущему пользователю или
состоянию frontend. Export coordinator не строит документ в браузере и не
дублирует серверные права.

## 10. Проверки

### 10.1. Страховочные проверки

До изменения закрепляются или расширяются characterization-тесты:

- существующие пять типов блоков, порядок строк и размеры колонок редактора;
- sticky-поведение панели форматирования;
- форматирование rich text;
- latest-wins metadata save;
- текущий CaptionPanels payload и авторизация.

### 10.2. Backend

Проверяются:

- upgrade чистой PostgreSQL и `NULL` для старого сюжета;
- свободный хронометраж, trim, пустое значение, лимит 64 и права;
- событие истории и `updated_at` без изменения technical revision;
- разрешённый экспорт активного и архивного сюжета;
- `401`, `404` и `409 EXPORT_SNAPSHOT_MISMATCH`;
- отсутствие изменений истории, времени и workflow от экспорта;
- безопасные заголовки ответа и имена файлов;
- отсутствие файлов в application storage и временных DOCX.

Структурные DOCX-тесты повторно открывают байты и проверяют:

- A4, поля, одну таблицу, объединение и ширины;
- три метастроки и три заголовка;
- все пять типов блоков;
- несколько файлов и TC;
- пустой хронометраж;
- разные run-level шрифты, жирный, курсив, зачёркивание и заливки;
- многостраничный длинный сценарий;
- отсутствие реальных данных и чувствительных core properties.

### 10.3. Frontend и browser

Component-тесты проверяют:

- визуальный перенос длинного названия без сохранения реального перевода
  строки;
- ввод, latest-wins сохранение и read-only хронометраж;
- flush строк и метаданных до экспортного запроса;
- блокировку повторного клика;
- отсутствие скачивания при save/conflict/network error;
- экспорт архивного сюжета без попытки сохранения.

Browser-проверка выполняется на `1366×768` и `1920×1080`:

- длинная шапка не ломает таблицу и не вызывает горизонтальную прокрутку;
- липкая панель с кнопкой остаётся видимой при прокрутке;
- редактирование непосредственно перед нажатием попадает в скачанный файл;
- браузер получает один непустой `.docx` с ожидаемым именем;
- документ открывается и повторно читается как OOXML.

Синтетический документ с длинным названием, всеми типами блоков, несколькими
файлами/TC и всеми форматами рендерится целиком в PNG. Каждая страница
проверяется визуально: нет обрезанного текста, наложений, пустых случайных
страниц и разъехавшихся колонок. Реальные референсные документы в этот тест не
входят.

### 10.4. Полные gates

Перед локальным завершением проходят:

```bash
cd backend && pytest -q
cd frontend && npm ci && npm test -- --run && npm run build
docker compose -f compose.yaml config
```

Также выполняются Product Reset evaluator, чистая сборка backend/frontend
образов, migration/seed/health/smoke, backup/restore rehearsal и проверка
CaptionPanels. Точные команды, файлы и ожидаемые результаты фиксируются в
отдельном implementation plan.

## 11. Документация, версия и интеграция

Функция является новой обратно совместимой возможностью и планируется как
`1.1.0` по принятому Semantic Versioning.

В реализации одновременно обновляются:

- `SPEC_RU.md`;
- `EVAL_RUBRIC_RU.md`;
- пояснение в `IMPLEMENTATION_PLAN_RU.md` о новом каноническом экспорте;
- `PROGRESS.md` по checkpoint-ам;
- dependency lock и license/provenance metadata;
- `CHANGELOG.md`, backend/frontend version metadata;
- эксплуатационные smoke и deploy/recovery документы, если их контракт
  затрагивается.

Работа выполняется в отдельной feature-ветке или worktree, начинается с тестов
и делится на вертикальные checkpoint-коммиты. После локальной реализации
выполняется CodeRabbit review локальных коммитов. Push, PR, merge, tag и deploy
требуют отдельной команды владельца продукта.

## 12. Критерии готовности

Работа готова к внешней интеграции только когда одновременно верно следующее:

- длинное название полностью видно и не нарушает автосохранение;
- свободный хронометраж сохраняется с согласованными правами и историей;
- одно нажатие выдаёт DOCX именно из последнего подтверждённого снимка;
- активный и архивный сценарии экспортируются по одному каноническому пути;
- таблица Word соответствует зафиксированному макету и отображению пяти типов
  блоков;
- поддерживаемое форматирование редактора сохранено на уровне фрагментов;
