# NewscastNavigator 1.0.1 — управление сотрудниками и версия приложения

Статус: утверждено владельцем продукта 30 июля 2026 года.

## 1. Назначение

Этот документ задаёт минимальный обратно совместимый патч после завершения
Product Reset. Патч не меняет редакционную модель, сценарий, CaptionPanels,
workflow или production gates.

Текущее завершённое состояние Product Reset на `main`
`33828d81e8489cdadcec2683f4c98a11d27538db` принимается за версию приложения
`1.0.0`. Следующий патч получает версию `1.0.1`.

Номера `1.0.0` и `1.0.1` относятся только к релизам приложения. Они не
возвращают ручные версии сценария, выбор актуального текста, branch/merge или
другие удалённые механизмы.

Существующее техническое значение `0.2.0` в package metadata относится к
прототипу до Product Reset и заменяется release baseline `1.0.0`; отдельная
публичная линия `0.x` не сохраняется.

## 2. Изменение логина

- Управлять логином может только пользователь с функцией `chief`.
- Логин редактируется в существующем диалоге «Изменить сотрудника».
- Используется та же нормализация, длина и проверка уникальности, что при
  создании сотрудника.
- При конфликте API возвращает стабильную ошибку `USERNAME_TAKEN`; введённые
  имя, должность и функции остаются в форме.
- Активная сессия привязана к идентификатору пользователя, поэтому смена логина
  не завершает текущую сессию. При следующем входе используется новый логин.
- Пароль и `must_change_password` при смене логина не меняются.

## 3. Безопасное удаление сотрудника

Начальник может полностью удалить только ошибочно созданную и ещё не
использованную учётную запись.

Удаление запрещено, если выполняется хотя бы одно условие:

- удаляется текущий пользователь;
- пользователь является последним активным начальником;
- пользователь был автором сюжета, назначенным сотрудником или назначал другого
  сотрудника;
- пользователь добавлял материалы;
- пользователь участвовал в событиях, редакторских сессиях или сохранённых
  состояниях сценария;
- пользователь отмечен в workflow, production, пакетах правок, внешнем
  согласовании или как actor уведомления;
- существует любая другая доменная или историческая ссылка, которую удаление
  могло бы обнулить или повредить.

Личные технические записи не считаются участием и удаляются вместе с
неиспользованной учётной записью: функции, сессии, маркеры чтения и уведомления,
где пользователь является только получателем.

Backend выполняет явную проверку всех доменных ссылок до удаления. Ограничения
внешних ключей остаются вторым fail-closed барьером. При блокировке API
возвращает `409 USER_DELETE_BLOCKED` и понятный текст:
«Сотрудник уже участвовал в работе. Отключите учётную запись».

API:

- `PATCH /api/v1/admin/users/{id}` принимает необязательный `username`;
- `DELETE /api/v1/admin/users/{id}` удаляет только допустимую учётную запись и
  возвращает существующий `CommandAck`.

## 4. Интерфейс

- В диалоге «Изменить сотрудника» появляется поле «Логин».
- В действиях строки появляется опасное действие «Удалить».
- Удаление требует явного подтверждения с именем и логином сотрудника.
- Во время команды остальные действия заблокированы.
- После успеха список перечитывается с сервера.
- Серверная причина отказа показывается рядом со списком и не маскируется общей
  ошибкой.
- Backend остаётся единственным источником разрешений и инвариантов.

## 5. Версионирование

Используется Semantic Versioning:

- `MAJOR` — несовместимое изменение продукта или публичных контрактов;
- `MINOR` — новая обратно совместимая возможность;
- `PATCH` — совместимое исправление или небольшой эксплуатационный патч.

Релизные значения backend и frontend обязаны совпадать. Репозиторный тест
сравнивает:

- `backend/pyproject.toml`;
- fallback в `backend/app/core/version.py`;
- `frontend/package.json`;
- `frontend/package-lock.json`.

История релизов ведётся в кратком актуальном `CHANGELOG.md`. Старое содержимое,
описывающее удалённую до Product Reset модель, не сохраняется в текущем
документе: архивом остаётся Git history.

После внешнего разрешения:

- тег `v1.0.0` указывает на baseline
  `33828d81e8489cdadcec2683f4c98a11d27538db`;
- тег `v1.0.1` создаётся на точном проверенном merge commit патча;
- production evidence связывает tag, commit и фактически запущенный SHA.

## 6. Мини-футер

На странице входа и в рабочем AppShell отображается один общий компактный
компонент:

`Newscast Navigator v1.0.1 · © 2026 Павел Курзыкин. Все права защищены.`

Футер:

- визуально вторичен и не конкурирует с рабочими действиями;
- находится в обычном потоке, не перекрывает редактор и не фиксируется поверх
  экрана;
- использует версию из frontend package metadata, а не отдельную строковую
  константу компонента;
- проверяется component- и browser-тестами на странице входа и после входа.

## 7. Политика browser cache

Чтобы новая версия гарантированно обнаруживалась браузером:

- HTML entry point и SPA fallback получают
  `Cache-Control: no-cache, must-revalidate`;
- файлы `/assets/*` с content hash получают
  `Cache-Control: public, max-age=31536000, immutable`;
- отсутствующий asset возвращает `404`, а не HTML fallback;
- health и API не затрагиваются.

Эта политика предотвращает повторение ситуации, когда ранее посещавший сайт
браузер запускает старый JavaScript после production cutover.

## 8. Проверки

Backend:

- chief-only изменение логина;
- нормализация и конфликт логина;
- запрет удаления себя и последнего активного начальника;
- удаление неиспользованного сотрудника;
- отдельный тест каждого класса исторических ссылок, включая ссылки с
  `ondelete=SET NULL`;
- удаление технических записей только допустимого пользователя;
- fail-closed обработка неожиданного `IntegrityError`.

Frontend:

- поле логина и сохранение через существующий edit dialog;
- отображение конфликта без потери остальных полей;
- подтверждение удаления, pending state, success refetch и серверный отказ;
- футер и единый номер версии.

Operations/browser:

- version-consistency test;
- nginx header tests для HTML, asset и отсутствующего asset;
- production build;
- browser flow chief: rename login, delete unused user, reject used user;
- чистый и ранее открывавшийся browser profile получают актуальный HTML;
- до deploy проходят все локальные hard gates, кроме закономерно устаревшего
  exact-SHA external evidence;
- после deploy создаётся отдельный evidence-only commit, и полный Product Reset
  evaluator проходит на точном новом `main`.

## 9. Развёртывание

Миграция БД не нужна. До переключения создаётся обычный backup PostgreSQL.

Новые backend и frontend images собираются, пока старые контейнеры обслуживают
production. Затем последовательно заменяются только `backend` и `frontend`.
`db`, `gateway` и legacy hot rollback не пересобираются.

Release выполняется в fail-closed порядке:

1. patch PR проходит тесты и merge;
2. merge commit разворачивается как exact app SHA;
3. production smoke и browser evidence подтверждают фактически запущенный SHA;
4. только после успешного smoke merge commit получает тег `v1.0.1`;
5. отдельный evidence-only PR связывает deploy с новым `main`;
6. финальный evaluator проверяется на точном evidence merge commit.

После переключения проверяются:

- exact deployed SHA и версия `1.0.1`;
- health, вход существующего `admin` и сохранность его password hash;
- rename/delete permissions и оба отказа удаления;
- cache headers и загрузка новой сборки;
- CaptionPanels smoke;
- rollback readiness.

## 10. Вне рамок

- удаление сотрудника, который участвовал в работе;
- каскадное удаление или анонимизация истории;
- изменение логина самим сотрудником;
- email, SSO, самостоятельная регистрация;
- пользовательские версии сценария;
- новая роль, мобильный интерфейс или параллельный runtime.
