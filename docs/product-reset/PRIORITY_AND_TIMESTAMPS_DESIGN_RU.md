# Управление приоритетом и даты в реестре сюжетов

Статус: утверждено владельцем продукта 28 июля 2026 года.

## 1. Цель

Сделать приоритет сюжета управляемым, не добавляя отдельного экрана, и показать в общем реестре время создания и последнего содержательного изменения сюжета.

## 2. Приоритет

- Допустимы только `Стандарт` и `Высокий`.
- При создании сюжета поле «Приоритет» имеет значение `Стандарт` по умолчанию.
- Начальник и шеф-редактор могут выбрать `Высокий` при создании.
- Пользователь без функции руководства не может установить или изменить высокий приоритет; при создании для него сохраняется `Стандарт`.
- В реестре руководство меняет приоритет через выпадающий список непосредственно в колонке «Приоритет».
- Для остальных пользователей приоритет остаётся статической меткой.
- После успешного изменения реестр получает подтверждённое сервером состояние; при ошибке прежнее значение остаётся видимым и выводится понятное сообщение.

## 3. Даты реестра

Справа от колонки «Исполнители» добавляются:

1. «Изменён» — дата и время последнего содержательного изменения сюжета.
2. «Создан» — дата и время создания сюжета.

Пользовательский формат: `28.07.2026, 19:15`, часовой пояс
`Europe/Moscow`.

«Изменён» обновляется при:

- сохранении текста сценария;
- изменении названия, рубрики, автора или приоритета;
- изменении назначений;
- workflow- и производственных действиях;
- добавлении или изменении рабочего контекста сюжета;
- внешнем согласовании, эфире, архивировании и восстановлении.

Простое чтение сюжета, открытие вкладки, edit-lease heartbeat и техническая доставка уведомлений дату не меняют.

## 4. Данные и API

- `stories.updated_at` становится каноническим временем последнего содержательного изменения агрегата сюжета.
- Все содержательные команды обновляют `stories.updated_at` в той же транзакции.
- `StoryListItem` возвращает `updated_at`.
- Создание сюжета принимает необязательный `priority`; отсутствие значения эквивалентно `standard`.
- Backend повторно проверяет право руководства на `high`, независимо от состояния интерфейса.
- Для изменения существующего сюжета используется leadership-only management command с полем `priority`.
- Read model сообщает frontend доступность управления приоритетом через серверную policy/action-модель, а не через дублирование правил доступа в компоненте.

## 5. Интерфейс

Порядок колонок:

1. Приоритет.
2. Название.
3. Рубрика.
4. Автор.
5. Что происходит.
6. Исполнители.
7. Изменён.
8. Создан.

Таблица остаётся desktop-only и не получает горизонтальную прокрутку на согласованных viewport. Даты отображаются компактно, без секунд.

## 6. Проверки

- Backend API: дефолт `standard`, leadership может создать/изменить `high`, остальные получают `FORBIDDEN`, список возвращает `created_at` и `updated_at`.
- Backend domain: содержательные команды меняют `updated_at`, read-only и технические действия не меняют.
- Frontend component: форма создания отправляет выбранный приоритет; таблица показывает восемь колонок и корректный формат дат; inline select доступен только при наличии server action.
- Browser: создание со стандартным и высоким приоритетом, изменение приоритета в таблице, сохранение сценария с обновлением «Изменён», отсутствие горизонтальной прокрутки.
- Актуализируются `SPEC_RU.md`, `EVAL_RUBRIC_RU.md`, `IMPLEMENTATION_PLAN_RU.md` и `PROGRESS.md`.

## 7. Вне рамок

- Новые значения приоритета.
- Отдельная страница управления приоритетами.
- Ручное редактирование дат.
- Сортировка по датам и новые фильтры.
- Обновление «Изменён» от просмотров, уведомлений или фоновых heartbeat.
