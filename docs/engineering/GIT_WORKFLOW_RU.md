# Git: от начала задачи до синхронизации

## Ответственность и разрешения

Координатор ведёт задачу, `repository-steward` проверяет Git и выполняет только
операции своего [ограниченного контракта](PROJECT_AGENTS_RU.md#контракт-делегирования).
Куратор документации проверяет содержание и навигацию документов, reviewer и
verifier — решение и доказательства. Куратор репозитория сверяет итоговый diff,
проверенный SHA, состояние PR/CI и сохранность истории перед интеграцией.

Работа ведётся в отдельной ветке/worktree, новые ветки Codex — `codex/<задача>`.
В `main` не создают прямые коммиты и не отправляют изменения в обход PR.
Обновление чистого локального `main` после принятого PR выполняется fast-forward.

Push, создание PR, merge, удаление веток/worktree и изменение защиты GitHub
выполняются по действующему разрешению. Владелец может одним поручением
разрешить перечисленную цепочку для конкретного репозитория и кандидата;
повторное согласование каждого входящего в неё шага не требуется. Изменившийся
существенный scope, неожиданные данные или операция вне цепочки требуют
отдельного решения. Git-интеграция не разрешает tag, release или deploy.

## 1. Начало работы

Координатор проверяет каталог, root, branch, HEAD, base, upstream и status:

```bash
git status --short --branch
git branch -vv
git worktree list --porcelain
git rev-parse HEAD
```

При расхождении refs, чужих изменениях, неясном upstream или нескольких
worktree вызывается куратор с конкретным вопросом. Обычная короткая проверка
чистого checkout не требует отдельного агента. Чужие изменения сохраняются.

Свежесть remote проверяется чтением GitHub или `git ls-remote --heads origin`.
Локальная ссылка `origin/main` может быть устаревшей. Ошибка сети означает
UNKNOWN; нельзя утверждать, что локальная и удалённая ветки совпадают.
`fetch` изменяет локальные refs и выполняется в рамках разрешённой Git-работы.

## 2. Реализация и проверка

Изменения поведения воспроизводятся тестом; каждый checkpoint завершается
проверками по [риску изменения](DEVELOPMENT_RU.md), self-review, актуальными
документами и осмысленным локальным commit. Перед commit:

```bash
git diff --stat
git diff --check
python3 scripts/check_docs.py
```

Для существенной правки reviewer и отдельный verifier проверяют один commit
или manifest файлов. После правок повторяются затронутые проверки. Проверки
документации и конфигурации агентов выполняются без запуска приложения;
серверная приёмка нужна по правилам [выпуска](../operations/RELEASE_WORKFLOW_RU.md).

После задачи с коммитами куратор репозитория обязательно получает итоговый
снимок. Он отличает локальную готовность от опубликованного и принятого результата.
Не коммитятся `.env`, секреты, рабочие datasets, зависимости и ignored evidence.
Lock-файлы коммитятся вместе с dependency inputs.

## 3. Публикация и PR

Перед push куратор проверяет полный diff против свежего base, владельца ветки,
отсутствие случайных файлов, результаты review/verification и пределы разрешения.
Ветка публикуется с upstream; PR содержит точный head/base, область изменения,
проверки и оставшиеся условия. Прежний зелёный CI не подтверждает новый head.
После исправлений CI должен относиться к последнему кандидату и текущему base.

Для `main` политика проекта требует PR и обязательные проверки GitHub:

- `Documentation structure and links`;
- `Backend and operations checks`;
- `Frontend tests and build`.

Защита должна требовать актуальную базу, запрещать force-push и удаление `main`,
распространяться на администраторов. Число обязательных человеческих approvals
может быть нулевым для одного владельца; независимые агентные review/verification
остаются обязательными по правилам проекта. Обсуждения должны быть разрешены.
Фактическое включение защиты подтверждается API; документ сам её не включает.
При недоступности настройки причина записывается, статус не объявляется PASS.

## 4. Сохранность истории и слияние

Перед merge найдите commit SHA, на которые ссылаются отчёты, manifests и карты
восстановления. Эти объекты должны оставаться достижимыми из постоянных refs
после удаления рабочей ветки. Для текущей документационной истории используется
**merge commit**: сохраняются исходные коммиты и их SHA. Squash/rebase для такой
ветки без отдельного решения о сохранении всех источников не подходят.

Куратор повторно сверяет разрешённый head, свежий base, CI и отсутствие блокеров.
Merge выполняется с проверкой ожидаемого head SHA. Если head/base изменились,
сначала новая сверка и затронутые проверки. Принятый commit, дата и PR записываются.

Merge создаёт новый SHA: проверьте итоговый diff/tree, CI на `main` и нужные
исторические объекты. Для выпуска приложения новый SHA также проходит
домашнюю приёмку по release workflow. Слияние документации само не запускает deploy.

## 5. Синхронизация и очистка

После принятого PR обновите только разрешённый чистый checkout:

```bash
git fetch origin
git switch main
git merge --ff-only origin/main
```

Проверьте равенство `local main == origin/main == remote main` по свежему чтению,
чистый status, достижимость исходных SHA и результат CI. При divergence, чужих
изменениях или неожиданном HEAD остановитесь; `reset --hard` не применяется.
Worktree другой активной задачи может иметь собственную ветку или detached SHA;
его не обновляют принудительно ради одинакового HEAD во всех каталогах.

Рабочая ветка удаляется после подтверждения интеграции и сохранности источников.
Для squash одного `git branch --merged` недостаточно: нужны merged PR, его
проверенный head и отсутствие последующих уникальных коммитов. Remote-ветка
удаляется только в пределах поручения. Не удаляйте текущую рабочую ветку.

Перед удалением worktree куратор проверяет:

- принадлежность завершённой задаче и отсутствие активной связанной задачи;
- отсутствие уникальных detached/unpublished коммитов;
- tracked, untracked **и ignored** файлы; чистый status не исключает local data;
- назначение локальных данных по метаданным, без чтения секретов/рабочих БД;
- управление каталогом приложением Codex и отсутствие символических обходов.

Неизвестное или ценные локальные данные означают KEEP с причиной и следующим
шагом. Общий `git clean -fdx`, принудительное удаление и обход symlinks запрещены.
Закрытие задачи в Codex и удаление worktree — отдельные действия с разрешением.

## 6. Итог и точка продолжения

В каждом итоге задачи с коммитами явно указываются:

| Этап | Доказательство |
|---|---|
| Реализовано | Commit и состав diff |
| Проверено | Команды, review/verification и точный объект |
| Опубликовано | Remote branch/head и PR |
| Интегрировано | Merged PR и SHA принятого результата |
| Синхронизировано | Свежие local/origin/remote SHA, чистый checkout |
| Убрано | Удалённые ветки/worktree и перечень KEEP с причинами |

Невыполненный этап отмечается `PENDING`, недоступная проверка — `UNKNOWN` или
`NOT_RUN` с причиной. Отдельно записываются оставшийся шаг и границы разрешения.
Результат реализации в Git может быть завершён при ожидающей интеграции;
полное закрытие Git объявляется только по доказательствам всех разрешённых этапов.

[Отчёт](../templates/report.md) в Git фиксирует проверенную реализацию и её
ограничения; итог внешних операций после merge фиксируется в связанном PR
и финальном ответе. PROJECT_STATE ведёт к этому PR. Не создавайте циклические
коммиты только ради записи SHA того же коммита. Прежние отчёты не переписываются
так, будто их исходный снимок уже был опубликован или проверен сервером.
