# UX/product stabilization plan - Newscast Navigator

Дата: 2026-05-14
Статус: implementation plan, без изменений кода продукта.
Цель: превратить текущий web UI в понятную рабочую newsroom-систему без нового визуального редизайна, без новых продуктовых фич и без наложения нового интерфейса поверх старого.

## Source of truth

При реализации считать источником истины в таком порядке:

1. `AGENTS.md`.
2. `docs/PROJECT_WORKFLOW_ARCHITECTURE_RU.md`.
3. Текущее уточнение продукта: главный список сюжетов - общий newsroom-реестр, а не персональная очередь.
4. Реальный web-код в `frontend/` и `backend/`.
5. Актуальные документы `docs/ENGINEERING_PLAN_RU.md`, `docs/GIT_WORKFLOW_RU.md`, `docs/STATE_SNAPSHOT_AND_NEXT_STEPS_RU.md`, `docs/WEB_SMOKE_CHECKLIST_RU.md`.
6. Документы UI redesign в `docs/superpowers/specs/2026-04-29-ui-redesign-concept-design.md` и `docs/superpowers/plans/2026-04-29-ui-redesign-implementation-plan.md` - только как исторический контекст уже выполненного редизайна, не как новый TODO.

Если документы и реальный UI расходятся, для UX-стабилизации считать правдой `PROJECT_WORKFLOW_ARCHITECTURE_RU.md` плюс текущее продуктовое уточнение про общий реестр. Старые планы редизайна не должны снова управлять структурой экранов.

## Диагноз

Текущий UI уже содержит правильные сущности newsroom-workflow: список сюжетов, карточку сюжета, текст, current text state, материалы, правки, производство, историю и роли. Основная проблема не в отсутствии модели и не в визуальном стиле, а в том, что пользователь видит слишком много равнозначных сигналов и не понимает:

- где он сейчас находится;
- это общий список сюжетов или его личная очередь;
- какой следующий рабочий шаг главный;
- какой текст текущий, проверенный и вычитанный;
- какие статусы важны именно для его роли;
- где ежедневная работа, а где администрирование.

Главный риск следующей реализации: повторить предыдущий сценарий и добавить новые экраны, вкладки или термины поверх существующих. Этот план запрещает такой путь: каждое изменение должно заменять, упрощать или переносить существующий элемент, а не создавать конкурирующую структуру.

## Anti-overlay contract

Перед каждым PR исполнитель обязан пройти короткий replacement gate:

1. Если добавляется новый пользовательский термин, старый конкурирующий термин удаляется или переименовывается в том же PR.
2. Если добавляется новый entry point, старый entry point удаляется, становится тем же маршрутом или явно переводится в фильтр/представление.
3. Если раздел карточки переносится, старая копия раздела удаляется.
4. Если `Моя работа` становится представлением общего списка, она не должна оставаться отдельной конкурирующей рабочей областью.
5. Если создается новый компонент-обертка, он должен заменить старый компонент в route/render tree в том же PR.
6. После PR в интерфейсе не должно быть двух разных ответов на вопросы:
   - где общий список всех сюжетов;
   - где мои сюжеты;
   - какой текст сейчас текущий;
   - что мне делать дальше;
   - где управлять пользователями.

Запрещено в рамках UX-стабилизации:

- делать новый визуальный редизайн;
- создавать второй список сюжетов рядом с текущим;
- создавать новую карточку сюжета поверх `EditorPage` без удаления старого пути;
- трогать `frontend/src/features/editor-core/` без отдельной необходимости и отдельного тестового плана;
- добавлять новые backend-фичи, если задача решается перестановкой, копирайтом, фильтрами и рольным decluttering;
- менять модель данных current text / checked / proofread без отдельного архитектурного решения.

## Текущая карта UI

Основные зоны на момент аудита:

- `frontend/src/App.tsx` - верхний view state: `main`, `editor`, `change_password`.
- `frontend/src/components/app-shell/AppShell.tsx` - shell, текущий пункт `Рабочая очередь`, статичный контекст `Карточка сюжета`.
- `frontend/src/pages/MainPage.tsx` - список сюжетов, быстрые фильтры, создание сюжета, admin/users block.
- `frontend/src/components/ProjectWorkQueue.tsx` - таблица/реестр сюжетов, статусы текста/производства/команды.
- `frontend/src/pages/EditorPage.tsx` - фактическая карточка сюжета и редактор в одном большом экране.
- `frontend/src/components/story-workspace/*` - header, навигация, overview, text state, production, comments, materials, history.
- `frontend/src/features/editor-core/*` - основной текстовый редактор; это зона повышенного риска.
- `frontend/src/shared/labels.ts` - пользовательские роли и термины.
- `frontend/src/features/projects/projectPriority.ts` и `frontend/src/features/projects/projectPresentation.ts` - производные статусы, приоритеты, сортировка и отображение.

Важные факты из аудита:

- Главный экран называется и ощущается как `Рабочая очередь`, хотя должен быть общим `Списком сюжетов` или `Реестром сюжетов`.
- `Моя работа` уже существует как фильтр, но навигационная рамка заставляет воспринимать весь экран как личную очередь.
- Admin/users UI смешан с ежедневным рабочим экраном.
- Карточка сюжета существует внутри `EditorPage`; отдельного `ProjectCardPage` нет.
- В карточке редактор текста не является первым рабочим местом, а окружен большим количеством статусов и панелей.
- Некоторые термины технические или смешанные: `newsroom workflow`, `handoff`, `Current`, `ресинк`, `revision`.
- В ролях frontend нет полноценного `operator`, хотя продуктовая модель требует оператора.

## Целевая UX-модель

### Стартовый экран

Стартовый экран после входа: общий `Список сюжетов`.

Это не персональная очередь. Это единый newsroom-реестр всех сюжетов, где пользователь видит рабочую картину и может быстро переключиться на нужное представление.

Обязательные представления внутри общего списка:

- `Все сюжеты`;
- `Мои сюжеты`;
- `Назначено мне`;
- `Ждет моего действия`;
- `В работе`;
- `Срочные`;
- `По статусу`;
- `По исполнителю`;
- `По выпуску/дате`.

`Моя работа` может остаться только как сохраненное представление/фильтр общего списка. Она не должна выглядеть как отдельная конкурирующая система.

### Общий список сюжетов

Список должен отвечать на вопросы:

- что это за сюжет;
- на каком он этапе;
- насколько срочный;
- кто ответственный;
- к какому выпуску/дате относится;
- что сейчас блокирует работу;
- кто должен сделать следующий шаг.

Поля первого уровня:

- название/slug сюжета;
- статус сюжета;
- выпуск/дата;
- приоритет;
- ответственный/назначенные роли;
- состояние текста;
- состояние материалов;
- состояние производства;
- главный следующий шаг.

Поля второго уровня или подробности строки:

- checked/proofread details;
- diff/change warnings;
- технические timestamps;
- детальная история;
- служебные API-подписи.

### Карточка сюжета

Карточка открывается из строки общего списка. Пользователь должен сразу понимать:

- он внутри одного сюжета;
- какой текущий статус сюжета;
- какой следующий шаг;
- кто ответственный;
- какой текст текущий, проверенный и вычитанный;
- есть ли изменения после проверки, вычитки, монтажа или титров.

Рекомендуемый порядок разделов:

1. `Обзор` - сжатая шапка сюжета, следующий шаг, ответственные, выпуск/дата, блокеры.
2. `Текст` - рабочий редактор и состояние current text.
3. `Материалы` - ссылки на исходники и внешние папки.
4. `Правки` - комментарии/замечания, если текущая структура хранит их как comments.
5. `Производство` - монтаж, титры, озвучка, операторские/монтажные handoff-состояния.
6. `История` - audit trail и события.

Не создавать отдельную новую карточку поверх `EditorPage`. Сначала стабилизировать существующий route и существующие `story-workspace` компоненты.

### Редактор текста

Редактор текста - основное рабочее место автора/редактора и critical path для downstream flows. Его нельзя ломать или пересобирать в рамках UX-стабилизации.

Правила:

- `frontend/src/features/editor-core/` не менять в первых PR.
- Переставлять можно контейнеры, заголовки, пояснения статусов и навигацию вокруг редактора.
- Явно показывать:
  - текущий текст;
  - кто назначил его текущим;
  - кем он проверен;
  - кем он вычитан;
  - устарела ли проверка/вычитка после новых правок;
  - были ли изменения после старта титров/монтажа.
- Не использовать формулировки, которые говорят об актуальной проверке или вычитке, если фактического `checked/proofread` состояния нет.

### Администрирование

Управление пользователями не должно быть частью ежедневного newsroom-экрана. Админка должна быть отдельной рабочей областью или отдельным view в shell, доступным только роли admin.

Цель: администратор управляет пользователями, но автор/шеф/монтажер не видят admin-интерфейс как часть своей ежедневной работы.

## Роли и сценарии

### Автор/редактор текста

Что хочет сделать: написать новый текст, исправить текст, ответить на правки, сделать рабочую версию пригодной для проверки.

Стартовый экран: `Список сюжетов`, представления `Назначено мне`, `Мои сюжеты`, `Ждет моего действия`.

Первое, что должен увидеть: свои сюжеты в контексте общего реестра, срочность, статус текста, следующий шаг.

Главное действие: открыть сюжет и перейти в `Текст`.

Нужные поля: название, выпуск/дата, приоритет, ответственный, text status, checked/proofread status, comments/changes warning.

Что мешает сейчас: экран называется как очередь, редактор не является очевидным главным рабочим местом, технические статусы и panels отвлекают.

Где может запутаться: какой текст текущий, означает ли `Current`, что текст уже проверен, что делать после комментария.

### Шеф-редактор

Что хочет сделать: увидеть состояние всех сюжетов, назначить работу, понять риски выпуска, проконтролировать тексты и ответственных.

Стартовый экран: `Список сюжетов`, по умолчанию `Все сюжеты` или сохраненное редакционное представление.

Первое, что должен увидеть: общий реестр с приоритетами, статусами, ответственными, блокерами и выпуском.

Главное действие: открыть проблемный сюжет, назначить/уточнить ответственного, проверить статус текста/правок.

Нужные поля: статус сюжета, приоритет, выпуск, ответственные, этапы текста/материалов/производства, следующий шаг, overdue/blockers.

Что мешает сейчас: `Моя работа` может конкурировать с `Все сюжеты`, в строке слишком много равных деталей, противоречивые срочные сигналы.

Где может запутаться: что является производственным риском, а что просто служебная деталь.

### Начальник

Что хочет сделать: быстро понять общую производственную картину без входа в каждую карточку.

Стартовый экран: `Список сюжетов`, представления `Все сюжеты`, `Срочные`, `В работе`, `По выпуску/дате`.

Первое, что должен увидеть: сколько сюжетов в работе, какие срочные, где блокеры, кто ответственный.

Главное действие: открыть только рискованные сюжеты или отфильтровать выпуск.

Нужные поля: статус, приоритет, выпуск, ответственный, next action, blockers.

Что мешает сейчас: ежедневная детализация текста/админки/технических слов может скрывать общую картину.

Где может запутаться: где список всех сюжетов и почему он называется рабочей очередью.

### Оператор

Что хочет сделать: проставить пути к исходникам, материалам, внешним папкам, убедиться, что материалы доступны.

Стартовый экран: `Список сюжетов`, представления `Назначено мне`, `Ждет материалов`, `По выпуску/дате`.

Первое, что должен увидеть: сюжеты, где нужны материалы или пути к исходникам.

Главное действие: открыть `Материалы` в карточке.

Нужные поля: статус материалов, выпуск/дата, ответственный оператор, путь/наличие исходников, следующий шаг.

Что мешает сейчас: роль `operator` не выражена в frontend-ролях, материалы не выглядят как отдельный рабочий путь оператора.

Где может запутаться: нужно ли ему идти в производство, текст или материалы.

### Монтажер

Что хочет сделать: понять, какой текст и материалы брать в работу, не взять устаревший текст.

Стартовый экран: `Список сюжетов`, представления `Назначено мне`, `Готово к монтажу`, `В работе`.

Первое, что должен увидеть: текущий вычитанный текст, материалы, production status, изменения после старта монтажа.

Главное действие: открыть карточку, проверить `Текст`, `Материалы`, `Производство`.

Нужные поля: current text state, proofread status, material links, production state, changed-after-production warning.

Что мешает сейчас: много равнозначных статусов, риск прочитать “последний” текст как пригодный для монтажа.

Где может запутаться: можно ли брать текст в работу, если checked/proofread пустые или устарели.

### Дизайнер титров

Что хочет сделать: взять текущий вычитанный текст для титров и увидеть изменения после старта титрования.

Стартовый экран: `Список сюжетов`, представления `Назначено мне`, `Титры`, `Ждет титров`, `Изменилось после титров`.

Первое, что должен увидеть: вычитан ли текущий текст и были ли изменения после старта титров.

Главное действие: открыть карточку и проверить `Текст` плюс production/titles status.

Нужные поля: current text state, proofread status, titles status, diff warning, updated_at/current_by.

Что мешает сейчас: technical `Current` и revision-сигналы требуют расшифровки, не всегда понятно, какой текст downstream-safe.

Где может запутаться: считать случайный последний workspace text источником для титров.

### Администратор

Что хочет сделать: управлять пользователями и доступами без смешивания с редакционной работой.

Стартовый экран: отдельный `Администрирование` entry point.

Первое, что должен увидеть: пользователи, роли, активность, действия управления.

Главное действие: создать/отредактировать пользователя, сбросить пароль, изменить роль/статус.

Нужные поля: login, display name, role, active, last login/updated where available.

Что мешает сейчас: admin block находится в `MainPage` вместе с реестром сюжетов.

Где может запутаться: администрирование выглядит частью newsroom-потока.

## Термины

Рекомендуемые замены:

- `Рабочая очередь` -> `Список сюжетов` или `Реестр сюжетов`.
- `Все проекты` / `Project` в пользовательском UI -> `Все сюжеты` / `Сюжет`.
- `Моя работа` -> оставить как представление, не как экран.
- `Current` -> `Текущий текст`.
- `workspace text` -> не показывать обычным пользователям; если нужно, `Рабочая версия`.
- `checked` -> `Проверено редактором`.
- `proofread` -> `Вычитано`.
- `handoff` -> `Передача в работу` или конкретно `Передано в монтаж`, `Передано в титры`.
- `revision` -> `Версия текста` или `Правка`.
- `ресинк` -> `Синхронизировать` только если это понятное действие, иначе скрыть.
- `newsroom workflow` -> не показывать в UI, заменить на конкретные рабочие статусы.

## Implementation sequence

Каждый stage должен идти отдельным маленьким PR. Нельзя объединять все stages в один огромный редизайн-PR.

Перед каждым stage:

1. `git status --short --branch`
2. `git diff --stat`
3. `git diff --name-only`
4. `git switch main`
5. `git pull --ff-only`
6. создать новую ветку с подходящим префиксом из `docs/GIT_WORKFLOW_RU.md`

После каждого stage:

1. `npm run build` в `frontend/`.
2. Targeted browser smoke через Playwright по сценариям stage.
3. Проверка, что не затронуты generated/build/lock files без причины.
4. Проверка replacement gate из этого плана.
5. Краткий отчет: что изменено, как проверить, риски.

### Stage 1 - Entry point и общий реестр

Цель: сделать стартовый экран явно общим `Списком сюжетов`, а не персональной очередью.

Примерная ветка: `refactor/ux-register-entrypoint`.

Зоны:

- `frontend/src/components/app-shell/AppShell.tsx`
- `frontend/src/pages/MainPage.tsx`
- `frontend/src/components/ProjectWorkQueue.tsx`
- `frontend/src/shared/labels.ts`
- возможно `frontend/src/styles.css` только для мелких layout fixes, без визуального редизайна

Действия:

- Переименовать пользовательский entry point `Рабочая очередь` в `Список сюжетов` или `Реестр сюжетов`.
- Перепроверить заголовки/empty states: экран должен объяснять, что это общий список.
- Оставить `Моя работа` только как быстрый filter/view внутри общего списка.
- Убрать или заменить формулировки, которые делают весь экран персональной очередью.
- Убедиться, что `Все сюжеты` является очевидным baseline view.

Что не трогать:

- `frontend/src/features/editor-core/*`
- backend API;
- модель данных;
- production/deploy.

Проверка:

- admin видит общий список и может выбрать `Все сюжеты`, `Моя работа`, `Назначено мне`.
- author начинает с общего списка, но может быстро включить персональный фильтр.
- в UI нет конкурирующих названий `Рабочая очередь` и `Список сюжетов` для одного экрана.
- `frontend` build проходит.

Риск: переименование может вскрыть старые тексты в тестах/smoke docs. Исправлять только актуальные документы/checklists, не archive.

Готовность:

- стартовый экран однозначно читается как общий newsroom-реестр;
- `Моя работа` не воспринимается отдельной структурой;
- old term не оставлен в навигации.

### Stage 2 - Views/filters вместо конкурирующих экранов

Цель: стабилизировать фильтры как сохраненные представления общего списка.

Примерная ветка: `refactor/ux-register-views`.

Зоны:

- `frontend/src/pages/MainPage.tsx`
- `frontend/src/components/ProjectWorkQueue.tsx`
- `frontend/src/features/projects/projectPriority.ts`
- `frontend/src/features/projects/projectPresentation.ts`
- `frontend/src/shared/types.ts` только если уже есть нужные поля и требуется типизировать существующую UI-логику
- `docs/WEB_SMOKE_CHECKLIST_RU.md` после изменения пользовательских сценариев

Действия:

- Привести quick filters к модели `представлений`: все, мои, назначено мне, ждет моего действия, в работе, срочные, по выпуску/дате.
- Проверить, что view labels не дублируют route labels.
- Добавить или переименовать views для production roles только если это использует уже существующие данные.
- Исправить противоречивые сигналы в строке: например, `Срочно` не должен соседствовать с `Нет срочного сигнала`.
- Поднять `next action`/blocker выше технических деталей.

Что не трогать:

- не создавать второй list component;
- не добавлять новые backend endpoints;
- не добавлять persistence saved views, если ее нет;
- не менять auth/roles model.

Проверка:

- переключение views не меняет route и не открывает новую рабочую область;
- `Все сюжеты` показывает общий реестр;
- `Мои сюжеты` и `Назначено мне` читаются как фильтры этого же реестра;
- срочные/приоритетные сюжеты не показывают противоречивые подписи;
- browser smoke desktop + mobile.

Риск: можно случайно спрятать общий список за персональными views. Baseline `Все сюжеты` должен оставаться первым и очевидным.

Готовность:

- пользователю понятно, что views - это способы смотреть один общий список;
- нет конкурирующей логики `my queue` vs `all projects`.

### Stage 3 - Упрощение карточки сюжета

Цель: сделать существующую карточку сюжета понятной без создания новой карточки поверх старой.

Примерная ветка: `refactor/ux-story-card-structure`.

Зоны:

- `frontend/src/pages/EditorPage.tsx`
- `frontend/src/components/story-workspace/StoryWorkspaceHeader.tsx`
- `frontend/src/components/story-workspace/StoryWorkspaceNav.tsx`
- `frontend/src/components/story-workspace/StoryWorkspaceStatusStrip.tsx`
- `frontend/src/components/story-workspace/StoryOverviewPanel.tsx`
- `frontend/src/components/story-workspace/StoryTextStatePanel.tsx`
- `frontend/src/components/story-workspace/StoryProductionPanel.tsx`
- `frontend/src/styles.css`

Действия:

- Сделать шапку карточки ответом на вопросы: сюжет, статус, следующий шаг, ответственные, выпуск.
- Упорядочить навигацию: `Обзор`, `Текст`, `Материалы`, `Правки`, `Производство`, `История`.
- Убедиться, что клик по `Текст` не приводит к перекрытию редактора sticky header'ом.
- Уменьшить видимость технических терминов в обычных панелях.
- Empty states для checked/proofread должны быть честными: если проверки нет, не писать как будто она актуальна.

Что не трогать:

- `frontend/src/features/editor-core/*`;
- сериализацию текста;
- API сохранения текста;
- новые статусы backend.

Проверка:

- из строки списка открывается карточка одного сюжета;
- `Текст` приводит к редактору без визуального перекрытия;
- current/checked/proofread states понятны без знания внутренних терминов;
- mobile smoke не показывает наложение текста и controls.

Риск: `EditorPage` большой и содержит много responsibilities. Менять только порядок/копирайт/контейнеры, не переписывать редактор.

Готовность:

- карточка объясняет следующий шаг;
- редактор находится как основное рабочее место;
- старые дубли panels не остались рядом.

### Stage 4 - Стабилизация редактора как рабочего места

Цель: не переписывая редактор, сделать его контекст очевидным для автора, редактора, монтажера и дизайнера титров.

Примерная ветка: `refactor/ux-text-workspace-context`.

Зоны:

- `frontend/src/pages/EditorPage.tsx`
- `frontend/src/components/story-workspace/StoryTextStatePanel.tsx`
- `frontend/src/components/story-workspace/StoryWorkspaceHeader.tsx`
- `frontend/src/components/story-workspace/StoryProductionPanel.tsx`
- `frontend/src/shared/labels.ts`
- `docs/WEB_SMOKE_CHECKLIST_RU.md`

Действия:

- Рядом с редактором показывать понятный summary: `Текущий текст`, `Проверено`, `Вычитано`, `Изменения после вычитки/титров/монтажа`.
- Скрыть или переименовать technical labels вокруг text state.
- Проверить, что пользователь не может принять случайную рабочую версию за downstream-safe text.
- Зафиксировать осторожный smoke around editor: открыть, внести тестовую правку в dev seed, сохранить, убедиться что состояние не сломано.

Что не трогать:

- editor-core extensions;
- serializers;
- block model;
- export contracts;
- CaptionPanels integration rules.

Проверка:

- author может найти редактор и сохранить текст;
- chief/editor видит checked/proofread state;
- designer/titles view видит warning, если текст изменен после титров;
- никаких regression в basic editing smoke.

Риск: любые изменения рядом с редактором могут сломать основное рабочее место. Поэтому запрещен refactor editor-core в этом stage.

Готовность:

- редактор работает как раньше;
- контекст current/checked/proofread стал понятнее;
- smoke checklist обновлен под фактические пользовательские шаги.

### Stage 5 - Role-based decluttering и админка

Цель: роли видят главное для себя, а администрирование отделено от ежедневной newsroom-работы.

Примерная ветка: `refactor/ux-role-decluttering-admin`.

Зоны:

- `frontend/src/App.tsx`
- `frontend/src/pages/MainPage.tsx`
- `frontend/src/components/app-shell/AppShell.tsx`
- новый или извлеченный компонент admin users, если он заменяет блок из `MainPage`, например `frontend/src/pages/AdminUsersPage.tsx` или `frontend/src/components/admin/*`
- `frontend/src/shared/labels.ts`
- `frontend/src/shared/types.ts`
- backend role definitions только после точечной проверки существующих API/DB enums

Действия:

- Вынести управление пользователями из `MainPage` в отдельный admin entry point.
- Убедиться, что admin UI недоступен и невидим для non-admin roles.
- Добавить/нормализовать frontend label для `operator`, если backend уже поддерживает роль.
- Для каждой роли убрать второстепенный шум с первого экрана через defaults/views/copy, без удаления данных из карточки.

Что не трогать:

- auth security model без отдельного security task;
- backend migrations без отдельного архитектурного решения;
- production credentials.

Проверка:

- admin видит `Администрирование` и может управлять пользователями;
- author/chief/operator/montager/designer не видят admin block в ежедневном списке;
- список сюжетов остается общим;
- role labels корректны и на русском.

Риск: если backend не поддерживает `operator` как роль, нельзя просто добавить frontend label и создать невалидное состояние. Сначала проверить API/types.

Готовность:

- администрирование отделено;
- роли не получают лишний admin noise;
- operator не потерян в UI.

### Stage 6 - Production smoke с реальными сценариями

Цель: подтвердить, что UX-стабилизация работает как newsroom workflow, а не только как набор проходящих билдов.

Примерная ветка: `docs/ux-production-smoke`.

Зоны:

- `docs/WEB_SMOKE_CHECKLIST_RU.md`
- при необходимости `docs/STATE_SNAPSHOT_AND_NEXT_STEPS_RU.md`
- screenshots only outside git unless специально нужны в docs

Действия:

- Обновить smoke checklist по ролям:
  - автор/редактор пишет или исправляет текст;
  - шеф-редактор контролирует все сюжеты;
  - начальник смотрит общую картину;
  - оператор проставляет материалы;
  - монтажер берет текст и материалы;
  - дизайнер титров проверяет вычитанный текст и изменения;
  - администратор управляет пользователями.
- Зафиксировать pre-PR checks для всех будущих UX changes.
- Отдельно записать known gaps, которые требуют product decision, а не UI patch.

Что не трогать:

- production deploy;
- реальные пользовательские данные;
- миграции.

Проверка:

- пройти checklist на dev/local;
- при необходимости пройти readonly smoke на staging/production только с разрешением;
- зафиксировать расхождения docs vs UI.

Риск: реальные пользователи могут выявить пробелы модели данных. Не маскировать это UI-копирайтом; вынести в отдельный архитектурный task.

Готовность:

- есть актуальный checklist перед каждым UX PR;
- роли и сценарии проверяемы;
- остаточные gaps явно записаны.

## Suggested autonomous execution model

Полностью автономная работа "от начала до конца" возможна только внутри заранее заданных границ. Чтобы снова не получить большой редизайн-клубок, безопасный режим такой:

1. Один stage = один PR.
2. Один PR = одна ветка от актуального `main`.
3. Агент может сам читать код, использовать skills, запускать subagents, вносить изменения, тестировать, коммитить и готовить PR только если пользователь явно разрешил git write/PR для implementation phase.
4. Агент не должен merge'ить PR, деплоить production или менять пользовательские данные без отдельного явного разрешения.
5. После каждого PR агент должен пройти replacement gate и smoke. Если gate не пройден, следующий stage не начинать.

Если пользователь хочет максимальную автономность без остановок, рекомендуемый компромисс:

- агент выполняет stages последовательно локально;
- после каждого stage делает commit на отдельной ветке или stacked branch;
- не merge'ит и не деплоит;
- возвращает список PR-ready branches и результаты проверок.

Более безопасный режим:

- запускать один stage за раз;
- после review/merge запускать следующий stage из свежего `main`.

## Agent/subagent decomposition

Использовать subagents только для независимых задач. Не параллелить изменения в одних и тех же файлах.

### Agent A - Register wording and views audit

Когда запускать: перед Stage 1 или Stage 2.

Зоны ответственности:

- `frontend/src/pages/MainPage.tsx`
- `frontend/src/components/ProjectWorkQueue.tsx`
- `frontend/src/components/app-shell/AppShell.tsx`
- `frontend/src/shared/labels.ts`

Входные документы:

- `AGENTS.md`
- `docs/PROJECT_WORKFLOW_ARCHITECTURE_RU.md`
- этот plan

Результат:

- список пользовательских терминов, которые нужно заменить;
- точные locations;
- предложения labels без изменений кода или небольшой patch только в назначенных файлах.

Можно параллелить: с Agent C documentation check.

Нельзя параллелить: с другим worker, который редактирует `MainPage.tsx` или `ProjectWorkQueue.tsx`.

### Agent B - Story card structure worker

Когда запускать: Stage 3.

Зоны ответственности:

- `frontend/src/pages/EditorPage.tsx`
- `frontend/src/components/story-workspace/*`
- `frontend/src/styles.css` only story-workspace selectors

Входные документы:

- `docs/PROJECT_WORKFLOW_ARCHITECTURE_RU.md`
- этот plan
- актуальный diff Stage 1/2

Результат:

- patch, который переупорядочивает карточку и исправляет text anchor/sticky overlap;
- список измененных файлов;
- browser smoke notes.

Можно параллелить: с documentation-only smoke checklist update, если нет shared files.

Нельзя параллелить: с Stage 4, потому что оба трогают `EditorPage` и text state panels.

### Agent C - Smoke checklist/documentation

Когда запускать: после каждого UI stage или в Stage 6.

Зоны ответственности:

- `docs/WEB_SMOKE_CHECKLIST_RU.md`
- при необходимости `docs/STATE_SNAPSHOT_AND_NEXT_STEPS_RU.md`

Входные документы:

- этот plan
- итоговый diff текущего stage
- фактические Playwright notes/screenshots

Результат:

- обновленный checklist;
- список manual smoke сценариев по ролям;
- зафиксированные расхождения docs vs UI.

Можно параллелить: с UI implementation, если docs не зависят от еще неготовых final labels.

Нельзя параллелить: с финальным docs update в тех же файлах.

### Agent D - Admin separation worker

Когда запускать: Stage 5.

Зоны ответственности:

- `frontend/src/App.tsx`
- `frontend/src/pages/MainPage.tsx`
- `frontend/src/components/app-shell/AppShell.tsx`
- admin extracted components/page
- `frontend/src/shared/labels.ts`

Входные документы:

- `AGENTS.md`
- `docs/PROJECT_WORKFLOW_ARCHITECTURE_RU.md`
- этот plan

Результат:

- admin users UI вынесен из daily register;
- old admin block удален из `MainPage`;
- role access smoke notes.

Можно параллелить: не параллелить с Agent A/Stage 1, если оба меняют `MainPage`.

Нельзя параллелить: с любыми изменениями shell/navigation в том же PR.

## PR order

Рекомендуемый порядок:

1. `docs/ux-product-stabilization-plan` - этот docs-only план.
2. `refactor/ux-register-entrypoint` - переименование entry point и baseline общего реестра.
3. `refactor/ux-register-views` - views/filters внутри общего реестра.
4. `refactor/ux-story-card-structure` - карточка сюжета без новой обертки.
5. `refactor/ux-text-workspace-context` - осторожный контекст вокруг редактора.
6. `refactor/ux-role-decluttering-admin` - role decluttering и отдельная админка.
7. `docs/ux-production-smoke` - финализация smoke checklist и known gaps.

Нельзя выполнять параллельно:

- PR 2 и PR 3, если оба меняют `MainPage.tsx`/`ProjectWorkQueue.tsx`.
- PR 4 и PR 5, потому что оба трогают `EditorPage`/text state.
- PR 5 и PR 6, если оба меняют `App.tsx`/`AppShell.tsx`/role labels.

Можно выполнять параллельно после фиксации labels:

- documentation smoke updates;
- read-only term audit;
- browser screenshot verification;
- проверку docs/code расхождений.

## Pre-PR checklist

Перед каждым PR:

- [ ] Проверен `git status --short --branch`, `git diff --stat`, `git diff --name-only`.
- [ ] PR не содержит generated/build/lock files без причины.
- [ ] Пройден replacement gate.
- [ ] Нет нового конкурирующего route/list/card для той же пользовательской задачи.
- [ ] `frontend/src/features/editor-core/` не изменен, кроме stage с отдельным разрешением.
- [ ] `npm run build` в `frontend/` проходит.
- [ ] Playwright smoke пройден минимум для admin и author; для role-specific stage - соответствующие роли.
- [ ] UI не смешивает admin и daily newsroom workflow.
- [ ] Пользователь может ответить: где все сюжеты, где мои сюжеты, что делать дальше, какой текст текущий.

## Completion definition for the whole UX stabilization track

Работа считается завершенной, когда:

- стартовый экран - общий `Список сюжетов`, а не персональная очередь;
- персональная логика реализована как views/filters общего списка;
- карточка сюжета не дублируется новым wrapper'ом поверх старого UI;
- редактор текста остался рабочим и стал легче находимым;
- current/checked/proofread states объяснены обычными русскими терминами;
- оператор, монтажер и дизайнер титров видят свои рабочие сигналы без лишней admin/technical нагрузки;
- админка отделена от ежедневной newsroom-работы;
- smoke checklist отражает реальные роли и сценарии;
- каждый PR был маленьким, проверяемым и не создавал конкурирующую структуру.
