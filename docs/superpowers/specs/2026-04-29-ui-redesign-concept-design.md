# Дизайн-спека: редизайн UI Newscast Navigator

Дата: 2026-04-29
Статус: draft для последующей реализации
Область: frontend UX/UI, без изменения backend/API на этом этапе

## 1. Цель

Редизайн должен превратить `Newscast Navigator` из набора рабочих экранов в понятную newsroom-систему управления одним сюжетом.

Главная пользовательская проблема:

- новый человек не понимает, где он находится;
- непонятно, что требует действия;
- список сюжетов выглядит как таблица данных, а не как рабочая очередь;
- редактор текста работает, но вокруг него не хватает понятной структуры карточки сюжета.

Целевое состояние:

- пользователь после входа понимает, что назначено лично ему;
- шеф-редактор и начальник видят, где процесс требует вмешательства;
- оператор, монтажер и дизайнер получают быстрый вход в свои производственные задачи;
- везде видно, какой текст является текущим, что проверено, что вычитано и что устарело;
- интерфейс говорит русскими рабочими терминами, без `current`, `handoff`, `diff`, `stale` в UI;
- существующий редактор текста не ломается и не переписывается первым этапом.

## 2. Принцип редизайна

Согласованный подход: **сначала UX-структура и дизайн-система, потом реализация экранов**.

Редизайн не должен быть хаотичной перекраской текущих компонентов. Сначала фиксируются:

- навигационная модель;
- ролевые стартовые фокусы;
- список сюжетов как главный рабочий компонент;
- карточка сюжета как единая workflow-оболочка;
- русский UX-словарь;
- визуальный характер интерфейса;
- ограничения по сохранению текущего редактора.

## 3. Визуальный характер

Согласованный стиль: **сдержанная newsroom-диспетчерская**.

Это означает:

- плотный, но читаемый рабочий интерфейс;
- минимум декоративных карточек;
- без лендинговой визуальности;
- без аналитического dashboard ради графиков;
- бренд Транснефти используется сдержанно: синий как основной, красный только для критичных сигналов;
- таблицы, статусы, фильтры и действия важнее визуальных эффектов;
- шрифты и финальная типографика требуют отдельной полировки, но композиция уже должна оставаться рабочей.

Опора на бренд:

- `docs/BRAND_GUIDELINES_TRANSNEFT_RU.md`;
- брендовые токены: `#00447C`, `#005596`, `#EE3124`, `#F3F6FA`, `#FFFFFF`;
- logo asset остается в `frontend/public/branding/`.

## 4. Русский UX-словарь

Внутренние backend/frontend имена могут оставаться английскими, если так устроена модель данных. В пользовательском интерфейсе используются русские термины.

| Не показывать пользователю | Показывать в UI | Смысл |
| --- | --- | --- |
| `current text` | текущий текст | состояние текста, по которому должны работать следующие этапы |
| `workspace text` | рабочий текст | живой редактируемый текст |
| `handoff` | передача на этап / передача в работу | момент передачи результата следующей роли |
| `stale` | устарело | текст изменился после проверки, вычитки, монтажа или титров |
| `diff` | что изменилось | сравнение старого и нового состояния |
| `proofread` | вычитано | корректор подтвердил конкретное состояние текста |
| `checked` | проверено | редактор/ответственный проверил конкретное состояние текста |

Примеры формулировок:

- “Текущий текст изменился после начала титров”.
- “Посмотреть, что изменилось”.
- “Передача в монтаж требует проверки”.
- “Рабочий текст новее текущего”.
- “Вычитка устарела”.

## 5. Ролевая модель главного экрана

Согласованный принцип: **роль задает стартовый фокус, но не ограничивает пользователя одним сценарием**.

Пользователь может вручную переключать режимы, потому что реальные роли пересекаются: шеф может править текст, дизайнер иногда может внести мелкую текстовую правку, монтажер может оставить замечание.

Стартовые фокусы:

| Роль | Стартовый фокус |
| --- | --- |
| начальник / шеф-редактор | Управление |
| автор / редактор текста | Моя работа |
| корректор | Моя работа |
| оператор | Производство → Материалы |
| монтажер | Производство → Монтаж |
| дизайнер | Производство → Титры |
| администратор | Моя работа + доступ к администрированию |

## 6. Основная навигация

Верхний уровень навигации должен быть укрупненным.

Разделы:

- **Моя работа** — все, что назначено лично пользователю.
- **Управление** — контроль для начальника/шефа: назначения, зависшие этапы, проблемы процесса.
- **Производство** — вкладки по этапам: Текст, Вычитка, Материалы, Монтаж, Титры, Финальная проверка.
- **Все сюжеты** — общий поиск, фильтры, полный список.
- **Архив** — завершенные и архивные сюжеты.
- **Администрирование** — пользователи, роли, служебные действия.

Не нужно делать отдельные “домашние страницы” для каждой роли. Нужен один layout с адаптированным стартовым фокусом.

## 7. Профиль пользователя

Профиль пользователя должен быть постоянным блоком в нижней части левой панели.

Содержимое:

- имя пользователя;
- роль / роли;
- сменить пароль;
- выйти;
- для администратора — быстрый доступ к администрированию;
- если требуется смена временного пароля — заметный сигнал в этом блоке.

Профиль не должен конкурировать с рабочей навигацией.

## 8. Главный экран

Главный экран строится вокруг списка сюжетов.

Композиция:

1. Левая навигация.
2. Заголовок текущего режима.
3. Компактная сводка.
4. Короткий главный сигнал.
5. Фильтры.
6. Список сюжетов как основной рабочий блок.

Сводка должна быть компактной, не крупными dashboard-карточками.

Пример сводки:

- `7 назначено мне`;
- `2 срочно`;
- `5 высокий приоритет`;
- `12 открытых правок`.

Главный сигнал:

- “Первым делом: сюжеты, где текст изменился после начала титров или монтажа”.

## 9. Список сюжетов

Пользовательское название: **Список сюжетов**.
Техническое рабочее имя в реализации может быть `ProjectList`, но не `StoryTable` в UI.

Список сюжетов — центральный компонент редизайна. Это не одна универсальная таблица со всеми полями, а общий паттерн с разными представлениями.

Общие правила:

- не показывать все поля одновременно;
- в одном представлении держать примерно 6-8 рабочих колонок;
- остальные детали открывать в карточке сюжета или раскрытии строки;
- строки должны объяснять причину попадания в очередь;
- у строки должен быть понятный следующий шаг.

Представления:

- **Моя работа**;
- **Управление**;
- **Производство**;
- **Все сюжеты**;
- **Архив**.

### 9.1. Представление “Моя работа”

Это не “мои проекты”, а очередь причин и действий.

Колонки:

- Сюжет;
- Почему здесь;
- Что сделать;
- Состояние;
- Приоритет;
- Действие.

Согласованная модель строки: **гибридная строка**.

- одна строка = один сюжет;
- внутри строки видно количество и краткий список задач;
- строку можно раскрыть прямо в списке;
- раскрытие показывает конкретные задачи и следующий шаг;
- основное действие ведет в карточку сюжета.

Пример:

- сюжет: “Итоги производственного совещания”;
- почему здесь: “Текст изменился после титров”;
- что сделать: “Посмотреть, что изменилось, и подтвердить передачу в титры”;
- состояние: “Титры устарели”, “Текущий текст есть”;
- приоритет: “Срочно · после начала титров”.

### 9.2. Представление “Управление”

Для начальника и шеф-редактора главный вопрос: **где процесс требует вмешательства**.

Колонки:

- Сюжет;
- Ответственные;
- Этапы;
- Проблемы;
- Активность;
- Действие.

Главные сигналы:

- нет исполнителя;
- зависший этап;
- открытые правки;
- нет текущего текста;
- текст изменился после передачи на монтаж или титры;
- давно нет обновлений.

Первый этап не должен превращаться в большой command center с графиками загрузки людей. Начинаем с практичного списка вмешательств.

### 9.3. Представление “Производство”

Для операторов, монтажеров, дизайнеров и тех, кто следит за передачей сюжета между этапами.

Вкладки внутри раздела:

- Текст;
- Вычитка;
- Материалы;
- Монтаж;
- Титры;
- Финальная проверка.

Колонки:

- Сюжет;
- Текущий текст;
- Материалы;
- Монтаж;
- Титры;
- Что изменилось;
- Открыть.

Главные сигналы:

- текст не готов к передаче;
- текст изменился после передачи;
- не хватает материалов;
- нужно посмотреть, что изменилось.

## 10. Приоритет

Слово “риск” в UI не используем как основную колонку. Согласованный термин: **Приоритет**.

Разделение смысла:

- **Состояние** отвечает на вопрос: что сейчас происходит с сюжетом.
- **Приоритет** отвечает на вопрос: в каком порядке этим заниматься.

Приоритет должен показываться вместе с причиной.

Примеры:

- `Срочно · текст изменился после начала титров`;
- `Высокий · вычитка устарела`;
- `Обычный · ждет вычитки`;
- `Низкий · недавно закрыто`.

Первичная градация:

| Приоритет | Примеры причин |
| --- | --- |
| Срочно | текст изменился после начала титров; текст изменился после начала монтажа; активный этап без исполнителя |
| Высокий | текущий текст устарел; вычитка устарела; есть назначенные открытые правки; нет текущего текста при активном производстве |
| Обычный | штатное действие; текст ждет проверки или вычитки; нужно дозаполнить материалы |
| Низкий | информационная задача; недавно закрытые правки; нет срочного действия |

Техническое правило для реализации:

- приоритет рассчитывается отдельно от UI;
- вход: данные сюжета, роль пользователя, статусы, правки, состояние текста;
- выход: уровень приоритета, причина, вес сортировки;
- правила должны быть легко дорабатываемыми без переписывания таблицы.

## 11. Карточка сюжета

Карточка сюжета — единое место жизни одного сюжета.

Вкладки:

- **Обзор**;
- **Текст**;
- **Правки**;
- **Материалы**;
- **Производство**;
- **История**.

Верх карточки:

- название сюжета;
- рубрика;
- общий статус;
- ответственные;
- время последнего обновления;
- основные действия;
- компактные бейджи состояния.

Компактные бейджи:

- “Текущий текст устарел”;
- “Проверено”;
- “Вычитка устарела”;
- “Титры требуют проверки”;
- “Монтаж: в работе”.

Не нужно дублировать одни и те же сигналы в трех местах. Согласованная модель:

- сверху только компактные состояния;
- внутри активной вкладки — одно главное действие или короткая контекстная панель;
- вторичный контекст держать ниже или в профильных вкладках.

### 11.1. Вкладка “Обзор”

Цель: за 10 секунд понять состояние сюжета.

Композиция:

1. Следующее действие.
2. Этапы производства.
3. Основные данные.
4. Ответственные.
5. Открытые правки.
6. Последние события.

Главный блок: **Следующее действие**.

Пример:

- “Назначить новый текущий текст и вернуть на вычитку”.
- “Рабочий текст новее текущего. После этого дизайнеру нужно посмотреть, что изменилось после начала титров”.

Этапы производства:

- Текст;
- Вычитка;
- Озвучка;
- Монтаж;
- Титры.

### 11.2. Вкладка “Текст”

Ключевое ограничение: **редактор текста остается рабочим ядром**.

Первым этапом мы не переписываем редактор. Новая карточка должна аккуратно обернуть существующий редактор.

Сохраняем:

- блоки текста;
- форматирование;
- версии;
- назначение текущего текста;
- проверку;
- вычитку;
- комментарии;
- экспорт;
- рабочие привычки пользователей.

Меняем осторожно:

- обрамление редактора;
- понятность статусов;
- вход в редактор из карточки;
- навигацию между зонами сюжета;
- русские формулировки действий.

Композиция вкладки:

1. Заголовок “Текст сюжета”.
2. Панель инструментов: сохранить рабочий текст, назначить текущим, что изменилось, экспорт.
3. Одна контекстная панель главного действия.
4. Существующий редактор как центральная рабочая область.
5. Вторичный контекст ниже, если нужен: участники, материалы, последние события.

Важно:

- не зажимать редактор боковыми панелями;
- не дублировать сверху и справа одни и те же предупреждения;
- улучшения самого редактора текста проектировать отдельным этапом после аудита.

## 12. Дизайн-компоненты

Первичная дизайн-система должна включать:

- боковую навигацию;
- профиль пользователя;
- компактную сводку;
- фильтры;
- список сюжетов;
- раскрытие строки;
- бейджи состояния;
- приоритет с причиной;
- карточку сюжета;
- вкладки карточки;
- панель главного действия;
- кнопки;
- поля ввода;
- пустые состояния;
- ошибки и успешные состояния.

## 13. Первый этап внедрения

Рекомендуемый порядок:

1. Закрепить документацию и UX-словарь.
2. Спроектировать компонентную структуру без переписывания editor core.
3. Обновить общий layout: sidebar, профиль, навигация.
4. Пересобрать главный экран вокруг списка сюжетов.
5. Ввести представления списка: Моя работа, Управление, Производство, Все сюжеты, Архив.
6. Ввести расчет приоритета отдельным слоем.
7. Пересобрать карточку сюжета с вкладками.
8. Встроить текущий редактор во вкладку “Текст”.
9. Отдельно проверить smoke-сценарии редактора.
10. Только после этого планировать улучшения самого редактора.

## 14. Что не делать

- Не переписывать редактор текста первым этапом.
- Не превращать продукт обратно в “только редактор текста”.
- Не делать отдельные интерфейсы для каждой роли.
- Не показывать английские технические термины пользователю.
- Не строить таблицу-простыню со всеми полями сразу.
- Не делать декоративный dashboard с графиками вместо рабочих очередей.
- Не использовать “риск” как непонятную цветную метку без функциональной нагрузки.
- Не добавлять новую архитектуру, которая ломает текущие contracts с `CaptionPanels`.

## 15. Связь с workflow-инвариантами

Редизайн обязан сохранять продуктовые инварианты из `docs/PROJECT_WORKFLOW_ARCHITECTURE_RU.md`:

- `Project` = одна карточка одного сюжета;
- рабочий текст и текущий текст — разные сущности;
- текущий текст должен быть явно виден;
- проверка и вычитка относятся к конкретному состоянию текста;
- если текст меняется после вычитки, вычитка устаревает;
- если текст меняется после начала титров или монтажа, это должно быть видно;
- дизайнер и downstream flows не должны опираться на случайный последний текст;
- связи с `CaptionPanels` и будущим `Premiere` plugin нельзя ломать.

## 16. Критерии готовности будущей реализации

Реализация редизайна считается успешной, если:

- новый пользователь понимает первый экран без объяснения разработчика;
- пользователь видит свои задачи и следующий шаг;
- шеф/начальник видит, где требуется вмешательство;
- оператор видит задачи по материалам;
- монтажер и дизайнер видят, изменился ли текст после передачи;
- список сюжетов не перегружен всеми полями сразу;
- приоритет помогает сортировать внимание;
- карточка сюжета не мешает редактору текста;
- редактор текста сохраняет текущие рабочие сценарии;
- UI использует русские пользовательские формулировки.
