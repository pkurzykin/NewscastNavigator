# План стабилизации UX workflow

Дата: 2026-04-22
Статус: выполнен (2026-04-22)
Ответственный контур: NewscastNavigator web

## 1. Цель

Закрыть оставшийся разрыв между текущей механикой action-комментариев и ежедневной newsroom-работой:

- явно показывать «что сейчас ждет моего действия»;
- явно показывать, что изменилось в тексте/ревизии с момента постановки задачи;
- сократить путь от задачи до конкретного места в проекте, где нужно внести изменение.

## 2. Границы работ

Входит в этап:

- UX-улучшения action-комментариев в `Main` и `Editor`;
- явный индикатор устаревания по каждому action-комментарию (`текст изменился после постановки задачи`);
- быстрый переход из элемента очереди в связанный контекст проекта;
- более четкие состояния жизненного цикла задачи (`open`, `in_progress`, `resolved`).

Не входит в этап:

- переделка ролевой модели;
- realtime-совместное редактирование уровня Google Docs;
- изменения на стороне других репозиториев/плагинов CaptionPanels.

## 3. Функциональные изменения

### 3.1 Ясная персональная очередь в Main

- Добавить отдельную группу «Мои задачи к действию» со стабильной сортировкой:
  1. назначено на меня + `open`
  2. назначено на меня + `in_progress`
  3. недавно закрыто мной
- Показать компактные бейджи по типу правки (`text`, `edit`, `titles`, `voiceover`, `final_review`, `other`).

### 3.2 Индикатор устаревания для дизайнера и редакторов

- Для каждого action-комментария рассчитывать, новее ли текущий `text_seq` проекта, чем `text_seq` на момент постановки задачи.
- Отрисовать явное предупреждение:
  - «Текст изменился после постановки задачи» с отображением `from_seq -> current_seq`.
- Дать переход в diff-контекст на базе уже существующих API сравнения текстовых состояний.

### 3.3 UX жизненного цикла задачи

- Сохранить текущие backend-поля workflow, но сделать переходы более прозрачными в UI:
  - `Open` -> `Take in work` -> `Resolve`
  - `In progress` -> `Release` (обратно в `Open`)
  - `Resolved` -> `Reopen`
- Добавить краткие системные пометки о переходах в истории проекта.

### 3.4 Нормализованная причина фокуса проекта

- В карточках очереди/проекта показывать единую причину попадания в фокус:
  - «Назначенная правка ждет выполнения»
  - «Задача в работе требует обновления»
  - «Закрытая задача переоткрыта»
- Максимально переиспользовать существующие backend-сигналы и счетчики, без тяжелого нового состояния.

## 4. План по backend

- Переиспользовать текущий payload action-комментариев и данные привязки к `text_seq`.
- При необходимости добавить вычисляемое поле причины фокуса:
  - `focus_reason` (string enum).
- Убедиться, что list-endpoints отдают достаточно данных, чтобы не плодить N+1 перезагрузки в `Main`.

На этом этапе миграция схемы БД не ожидается, если в ходе реализации не обнаружится отсутствующий обязательный флаг.

## 5. План по frontend

- `MainPage`:
  - уточнить группировку и фильтрацию персональной очереди;
  - отрисовать бейджи типа правок и `focus_reason`;
  - добавить прямой переход в проект и контекст конкретного комментария.
- `EditorPage`:
  - показать предупреждение об устаревании для релевантных комментариев;
  - сделать явные кнопки workflow-действий с корректными ограничениями по состоянию;
  - добавить быстрый переход в diff при зафиксированном устаревании.

## 6. План тестирования

Backend:

- расширить smoke/API-тесты для вычисления причины фокуса (если поле будет добавлено);
- проверить, что переходы жизненного цикла сохраняют ролевые ограничения.

Frontend:

- добавить interaction-тесты (или минимальные интеграционные проверки) для:
  - группировки очереди,
  - видимости индикатора устаревания,
  - доступности кнопок перехода состояний.

Ручной smoke:

- сценарий дизайнера: задача назначена -> текст изменился -> предупреждение видно -> diff открывается -> задача обновлена/закрыта;
- сценарий шеф-редактора: переоткрыть закрытую задачу и проверить обновление очереди у исполнителя.

## 8. Критерии готовности

- Назначенные пользователи сразу видят и обрабатывают свои ожидающие action-задачи.
- Дизайнер/редакторы явно видят рассинхронизацию текста после постановки задачи.
- Переходы жизненного цикла задачи предсказуемы и аудируются через историю.
- Нет регрессии в существующих тестах action-комментариев и workflow проекта.
