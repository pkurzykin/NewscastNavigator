# MVP Newsroom UI Design

Дата: 2026-05-20
Статус: draft для утверждения перед implementation plan
Основано на: `docs/superpowers/specs/2026-05-20-mvp-newsroom-service-design.md`

## 1. Цель

Спроектировать визуальную архитектуру `NewscastNavigator` до реализации, чтобы рабочая workflow-модель не превратилась в нагромождение карточек, кнопок и статусов.

UI должен ощущаться как современный рабочий newsroom-сервис:

- плотный;
- спокойный;
- управленчески понятный;
- быстрый для ежедневной работы;
- без маркетинговой композиции;
- без визуального шума;
- без возврата к модели “просто текстовый редактор”.

## 2. Главный UI-Принцип

Каждый экран должен отвечать на четыре вопроса:

1. Где я нахожусь?
2. Что сейчас главное?
3. Что блокирует движение?
4. Какое действие нужно сделать дальше?

Если экран не отвечает на эти вопросы, он не готов к реализации.

Запрещенный результат:

```text
много равных блоков
много равных кнопок
много равных статусов
карточки внутри карточек
технические термины в UI
одинаковый интерфейс для всех ролей
```

Целевой результат:

```text
один рабочий контекст
один главный блокер
один главный CTA в текущем контексте
сводка треков вместо стены деталей
детали раскрываются по необходимости
роль видит свой рабочий слой
```

## 3. Визуальное Направление

Стиль:

- операционный сервис;
- newsroom/production dashboard;
- не landing page;
- не декоративный dashboard;
- не набор “красивых карточек”;
- не темная киношная монтажная;
- не яркая SaaS-витрина.

Визуальная метафора:

```text
редакционный пульт управления производством роликов
```

Интерфейс должен быть достаточно плотным, чтобы шеф видел общую картину, но не перегруженным. Для этого:

- таблицы и списки важнее декоративных карточек;
- статусные индикаторы компактные;
- цвет используется для приоритета и блокеров, а не для украшения;
- детали треков раскрываются внутри карточки, но не показываются все одновременно;
- история и аудит находятся ниже по иерархии.

## 4. Бренд И Визуальные Токены

Использовать `docs/BRAND_GUIDELINES_TRANSNEFT_RU.md`.

Канонические цвета:

- brand blue primary: `#00447C`;
- brand blue accent: `#005596`;
- brand red accent: `#EE3124`;
- surface: `#FFFFFF`;
- background: `#F3F6FA`.

Типографика:

- заголовки и интерфейсные акценты: Franklin Gothic stack;
- основной текст: PT Sans stack.

Правила:

- не превращать UI в однотонную синюю тему;
- красный использовать только как акцент риска/критичного блокера;
- использовать нейтральные серые/белые поверхности для плотности;
- избегать больших градиентов, декоративных орбов, hero-блоков;
- радиусы карточек и панелей держать сдержанными, до 8px;
- сохранять читаемость на плотных экранах.

## 5. Информационная Архитектура

Основные разделы:

```text
Реестр
Карточка
Архив
Выпуск новостей
Администрирование
```

`Реестр` — стартовый экран для всех рабочих ролей.

`Карточка` — рабочее место одного сюжета.

`Архив` — отдельное представление, не часть ежедневного активного списка.

`Выпуск новостей` — группировка сюжетов, не обязательный контейнер всего процесса.

`Администрирование` — отдельно от newsroom-работы, видит админ.

Не делать отдельный конкурирующий раздел `Моя работа`. Это представление внутри реестра.

## 6. Главный Реестр

### 6.1 Назначение

Реестр показывает все активные карточки:

- исходники;
- сюжеты;
- производство;
- согласование;
- сдано.

Архив скрыт в отдельном представлении.

### 6.2 Форма Экрана

Утвержденная базовая форма для desktop: плотный реестр с правым предпросмотром выбранной карточки.

Не использовать карточный masonry/list как основную форму. Карточки допустимы только для мобильной адаптации или для повторяющихся компактных summary-элементов.

Базовая структура:

```text
верхняя панель:
  название сервиса
  представление
  поиск
  фильтры
  создать карточку

левая/центральная зона:
  название
  стадия
  главный блокер
  владелец
  команда
  треки
  срок/приоритет
  действие

правый предпросмотр:
  выбранная карточка
  главный блокер
  команда
  сводка треков
  главное действие
  последнее событие
```

Правый предпросмотр не должен становиться полной карточкой внутри реестра. Его задача — дать шефу/шеф-редактору быстрый управленческий summary и помочь решить, нужно ли открывать карточку.

На узких экранах правый предпросмотр убирается: остается список, открытие карточки происходит отдельным экраном.

### 6.3 Представления

Представления — это сохраненные фильтры одного реестра:

- Все активные;
- Мои;
- Исходники;
- Текст;
- Озвучка;
- Вычитка;
- Монтаж;
- Титры;
- Согласование;
- Сдано;
- Срочные;
- Выпуск новостей;
- Архив.

Представления не должны выглядеть как разные продукты.

### 6.4 Строка Реестра

Строка должна отвечать:

- что это;
- на какой стадии;
- что блокирует;
- кто владеет процессом;
- кто сейчас нужен;
- какие треки в риске;
- куда открыть.

Пример:

```text
Объект после модернизации
Стадия: Производство
Блокер: нет актуальной озвучки
Владелец: Иванова
Треки: текст OK, озвучка устарела, монтаж в работе, титры рано
Действие: открыть карточку
```

### 6.5 Главный Блокер

У каждой активной карточки в реестре должен быть один вычисленный главный блокер.

Примеры:

- не назначен монтажер;
- нет пути к исходникам;
- текст ждет проверки;
- озвучка устарела;
- монтаж не принят;
- титры устарели;
- есть замечания внешнего согласования;
- готово к отметке “отправлено на согласование”.

Если блокеров несколько, UI показывает главный, а остальные раскрываются в карточке.

### 6.6 Зафиксированный Wireframe

Для главного реестра принят вариант:

```text
Desktop: активный реестр + правый предпросмотр.
Narrow/mobile: список без предпросмотра + открытие карточки отдельным экраном.
```

Карточная доска по стадиям не используется как основной экран, потому что стадии и production-треки параллельны и быстро создают визуальный шум.

## 7. Создание Карточки

Главная кнопка:

```text
Создать карточку
```

Первый выбор:

- Исходники / материал;
- Сюжет в работу.

Утвержденная базовая форма: одна команда `Создать карточку`, затем выбор стартового типа. Это не две разные системы, а две начальные стадии одной карточки в общем реестре.

### 7.1 Исходники

Минимальная форма:

- дата;
- название;
- путь в архиве.

Никаких обязательных рубрик, ролей и сроков.

### 7.2 Сюжет

При оформлении как сюжет:

- рубрика обязательна;
- владелец процесса ставится автоматически;
- роль-слоты можно заполнить сразу или позже;
- пустые слоты видны как управленческий пробел.

Форма должна быть короткой. Расширенные поля доступны после создания карточки.

При создании сюжета нельзя требовать production-поля, которые еще не известны. Цель формы — быстро завести рабочий объект, а не заполнить всю будущую историю сюжета заранее.

## 8. Карточка Сюжета

### 8.1 Назначение

Карточка — рабочее место одного сюжета, а не страница с набором независимых виджетов.

Она должна показывать:

- состояние карточки;
- главный блокер;
- владельца процесса;
- команду;
- текущий production text;
- треки;
- замечания;
- историю.

### 8.2 Верх Карточки

Верх карточки должен содержать:

```text
название
рубрика
стадия
главный блокер
владелец процесса
главное действие
```

Главное действие одно в текущем контексте. Дополнительные действия в меню или вторичной панели.

### 8.3 Структура Карточки

Утвержденная базовая структура: `command layout`.

Карточка открывается как рабочее место сюжета, где сначала видны состояние, главный блокер, текстовый контекст и главный CTA. Production-треки показываются компактной сводкой и раскрываются по необходимости.

Рекомендуемая структура:

```text
Header:
  название, стадия, блокер, CTA

Summary strip:
  команда, text state, production text, финальный ролик

Main work area:
  текущий активный рабочий участок

Track rail:
  текст / озвучка / вычитка / материалы / монтаж / титры / согласование

Lower area:
  замечания, история, аудит
```

Не делать семь больших равных вкладок, каждая из которых выглядит одинаково важной.

Не использовать dashboard-сетку, где текст, озвучка, вычитка, материалы, монтаж, титры, согласование, правки и история становятся равными карточками. Такой вариант создает визуальное нагромождение и плохо показывает, что сейчас главное.

Навигация внутри карточки должна быть короткой:

```text
Обзор
Текст
Производство
Согласование
История
```

Отдельные треки не становятся отдельными крупными вкладками первого уровня. Они раскрываются внутри `Производство` или через status strip.

### 8.4 Треки

Треки в карточке должны быть компактной сводкой.

Каждый трек показывает:

- статус;
- исполнителя;
- связанную версию текста, если применимо;
- актуальность;
- основной action.

Детали трека раскрываются по клику.

Пример:

```text
Озвучка
Статус: устарела
По тексту: #5
Текущий текст: #6
Action: загрузить новую / подтвердить не требуется
```

## 9. Текстовое Рабочее Место

Текстовый редактор не переписывается.

Текст сюжета — главный содержательный объект карточки. При открытии карточки пользователь должен сразу видеть текстовый контекст: текущий текст или компактный preview текущего текста, статус text state и быстрый переход в полноценный редактор.

Нельзя проектировать карточку так, чтобы текст был спрятан глубоко за несколькими вкладками, ниже production-панелей или среди вторичных блоков.

UI вокруг редактора должен показывать:

- карточку сюжета;
- путь к исходникам;
- кто автор;
- состояние workspace draft;
- последний text state;
- проверку;
- вычитку;
- current production text;
- warnings: изменилось после озвучки/монтажа/титров.

Авторский сценарий:

```text
рабочий черновик
→ отправить на проверку
→ text state
```

Нельзя показывать autosave как production-версию.

Кнопка `Отправить на проверку` должна быть главным действием автора, когда текст готов.

### 9.1 Компоновка Раздела `Текст`

В command layout редактор не является маленькой панелью внутри overview. Когда пользователь открывает раздел `Текст` или главный CTA ведет в текст, центральная область карточки становится текстовым рабочим местом.

При открытии карточки overview тоже должен содержать заметный текстовый preview:

```text
текущий текст / production text
статус: черновик, на проверке, проверен, вычитан
кто и когда зафиксировал state
кнопка: открыть текст
```

Если сюжет еще на стадии исходников и текста нет, на месте preview показывается следующий шаг:

```text
текст еще не создан
оформить сюжет / открыть редактор
```

Рекомендуемая desktop-компоновка:

```text
верх:
  название сюжета
  стадия
  главный блокер
  главное действие

status strip:
  черновик
  последний text state
  проверка
  вычитка
  current production text

основная зона:
  слева: контекст сюжета, исходники, команда
  центр: существующий editor-core / таблица текста
  справа: workflow, замечания, отправка на проверку, предупреждения
```

Редактор и таблица текста должны занимать центральную и самую большую область. Слева и справа допускаются только поддерживающие панели, которые помогают писать и передавать текст дальше.

Запрещено:

- вставлять редактор в маленькую карточку;
- перекрывать рабочую таблицу production-статусами;
- делать production-треки равными по визуальному весу редактору на текстовом экране;
- менять editor-core как часть общей UI-перестройки без отдельного плана.

## 10. Production UI

Утвержденная базовая форма раздела `Производство`:

```text
верх:
  сюжет, стадия, главный блокер, главный CTA

track strip:
  текст, озвучка, вычитка, материалы, монтаж, титры, согласование

центральная зона:
  production gates
  текущий рабочий трек

правая зона:
  контроль шефа/шеф-редактора
  внутренние проверки
  разрешение черновых титров
  последнее событие
```

Production UI не должен быть сеткой из семи равнозначных больших панелей. Треки показываются компактно, а главная визуальная логика строится вокруг gates:

```text
озвучка готова
→ монтаж с озвучкой
→ проверка монтажа
→ титры
→ проверка титров
→ внешнее согласование
```

### 10.1 Параллельные Задачи

После проверки текста карточка показывает несколько активных треков:

- озвучка;
- вычитка;
- монтаж.

Реестр показывает сводку, карточка показывает детали.

### 10.2 Озвучка

UI озвучки:

- загрузить аудио;
- скачать текущую озвучку;
- показать text state озвучки;
- показать актуальность;
- показать предупреждение при изменении текста;
- дать шефу/шеф-редактору override `перечитка не нужна`.

Не показывать поле пути для озвучки в MVP.

### 10.3 Монтаж

UI монтажа:

- путь к монтажному ролику;
- статус монтажа;
- актуальная озвучка;
- text state основы;
- warning при изменении текста;
- action `отправить на проверку монтажа`;
- результат проверки: OK или правки.

### 10.4 Черновые Титры

До OK монтажа дизайнер не получает автоматический финальный шаг титров.

Шеф/шеф-редактор может явно нажать:

```text
Разрешить черновые титры
```

После этого дизайнер видит задачу:

```text
Сделать черновые титры
```

с предупреждением:

```text
Монтаж еще не принят. Титры черновые.
```

### 10.5 Финальные Титры

Финальные титры доступны после `Монтаж OK`.

UI должен строго показывать:

- по какой версии текста делались титры;
- какая версия текущая;
- если текст изменился, титры устарели;
- override невозможен;
- нужна перетитровка.

## 11. Внутренние Проверки

Два gate должны быть видны в карточке:

1. Проверка монтажа.
2. Проверка титров.

Они не должны быть спрятаны в истории.

Проверка монтажа:

- ролик с финальной озвучкой;
- шеф/шеф-редактор смотрит;
- OK или правки по монтажу.

Проверка титров:

- ролик с титрами;
- шеф/шеф-редактор смотрит;
- OK или правки по титрам.

Только после OK титров появляется действие:

```text
Отметить отправку на согласование
```

## 12. Внешнее Согласование UI

UI не должен выглядеть как интегрированный approval-сервис.

Утвержденная базовая форма:

```text
левая/центральная зона:
  готовность к внешнему согласованию
  текущий цикл
  история циклов

правая зона:
  зафиксировать результат
  если есть замечания: форма замечания к ролику
```

Нужны только действия:

- отметить `отправлено на согласование`;
- зафиксировать результат;
- указать замечания к ролику;
- выбрать видимую зону замечания;
- указать внутренние последствия;
- выбрать полный путь или быстрый путь, если применимо.

Результат `ok` автоматически ставит `Сдано`.

Отдельной кнопки `Сдать ролик` нет.

Внешнее согласование не должно показывать:

- способ отправки как обязательное поле;
- внешних согласующих как пользователей;
- upload/отправку ролика из системы;
- approval-ссылки;
- отдельный пакет отправки.

## 13. Замечания К Ролику

Форма замечания должна быть простой:

```text
Комментарий
Видимая зона: титры / озвучка / видео-монтаж / другое
Внутренние последствия:
  - изменить source text
  - перетитровать
  - новая озвучка
  - перемонтаж
Режим:
  - полный внутренний просмотр
  - быстрый путь после исправления
```

UI должен помогать не забыть последствия:

- если `изменить source text`, показать предупреждение о text state;
- если `перетитровать`, назначить дизайнеру;
- если `новая озвучка`, показать upload;
- если `перемонтаж`, назначить монтажеру.

## 14. Role-Based Decluttering

Один продукт, но разные роли должны видеть разные акценты.

Утвержденный подход: роли используют один общий реестр и одну карточку, но с разными представлениями, приоритетами и доступными действиями.

Не делать отдельные конкурирующие приложения:

```text
отдельная авторская система
отдельная монтажная система
отдельная дизайнерская система
отдельная очередь шефа
```

Вместо этого:

```text
единый реестр
→ фильтр / представление
→ роль-ориентированные CTA
→ скрытие лишних вторичных действий
```

Важно различать:

- `не показывать как главное`;
- `запретить действие правами`.

То, что действие скрыто визуально, не заменяет backend permission check.

### 14.1 Шеф / Шеф-Редактор

Видит:

- весь реестр;
- главный блокер;
- пустые роль-слоты;
- внутренние gates;
- внешнее согласование;
- архивирование.

Главные действия:

- назначить роли;
- проверить текст;
- проверить монтаж;
- проверить титры;
- отметить отправку;
- зафиксировать результат;
- архивировать.

### 14.2 Автор / Редактор

Видит:

- свои карточки;
- текст;
- замечания по тексту;
- состояние проверки;
- путь к исходникам.

Главное действие:

- открыть текст;
- отправить на проверку;
- исправить замечания.

Не показывать автору управленческие действия шефа как равные.

### 14.3 Корректор

Видит:

- карточки на вычитке;
- проверенный text state;
- editor context;
- action `завершить вычитку`.

Главное действие:

- вычитать;
- завершить вычитку.

### 14.4 Монтажер

Видит:

- материалы;
- актуальную озвучку;
- current production text;
- монтажный путь;
- правки по монтажу;
- предупреждения об устаревании.

Главное действие:

- указать монтажный файл;
- отправить монтаж на проверку;
- закрыть правку по монтажу.

### 14.5 Дизайнер Титров

Видит:

- разрешены ли черновые титры;
- принят ли монтаж;
- текущий text state;
- актуальность текста;
- правки по титрам;
- требование перетитровки.

Главное действие:

- сделать черновые титры;
- финализировать титры;
- исправить титры.

### 14.6 Администратор

Админка отдельно.

Админ может:

- управлять пользователями;
- технически поправить назначения;
- не участвует в production-flow как обычная роль.

### 14.7 Архив И Админка

Утвержденная UI-граница:

- архив — отдельное представление, визуально отделенное от активного реестра;
- `Сдано` остается в активном реестре до ручного архивирования;
- архивировать могут шеф, шеф-редактор и администратор при необходимости;
- админка — отдельный раздел для пользователей, ролей, доступа и временных паролей;
- управление пользователями не показывается внутри карточки сюжета;
- админские действия не становятся частью production-треков.

Архив должен поддерживать поиск и фильтры по:

- названию;
- рубрике;
- периоду;
- владельцу процесса;
- выпуску новостей, если применимо.

Админка должна оставаться утилитарной и не конкурировать визуально с newsroom-реестром.

## 15. Статусы И Русские Термины

Пользовательские термины должны быть русскими и рабочими.

Использовать:

- Исходники;
- Оформлено как сюжет;
- Текст пишется;
- На проверке;
- Проверено;
- На вычитке;
- Вычитано;
- Озвучка нужна;
- Озвучка готова;
- Озвучка устарела;
- Монтаж в работе;
- Монтаж на проверке;
- Монтаж OK;
- Черновые титры;
- Титры готовы;
- Титры устарели;
- Отправлено на согласование;
- Правки после согласования;
- Сдано;
- Архив.

Избегать в UI:

- `text_seq`;
- `workspace`;
- `handoff`;
- `track`;
- `proofread`;
- `final_review`;
- `sync required`;
- `stale`.

Технические термины допустимы в коде и документации, но не как основной пользовательский язык.

## 16. Empty / Loading / Error States

Каждое представление должно иметь рабочие состояния.

Пустой реестр:

```text
Нет активных карточек
Создать карточку
```

Пустое представление `Мои`:

```text
Нет карточек, где вам нужно действие
```

Пустой трек:

```text
Монтажер не назначен
Назначить монтажера
```

Ошибка загрузки:

```text
Не удалось загрузить реестр
Повторить
```

Не показывать длинные инструкции прямо внутри приложения.

## 17. Адаптивность

Desktop-first, потому что это рабочий newsroom-сервис.

Desktop:

- таблица реестра;
- широкая карточка;
- треки в rail/strip;
- редактор занимает центральное место.

Tablet:

- реестр может стать плотным списком;
- детали строки раскрываются.

Mobile:

- доступ к просмотру и небольшим действиям;
- не оптимизировать тяжелое производство под mobile как основной сценарий.

## 18. Wireframe Gate

Перед implementation plan нужно сделать browser wireframes минимум для:

1. Главный реестр.
2. Карточка сюжета: overview.
3. Текстовое рабочее место с существующим редактором.
4. Production-треки.
5. Внутренние проверки.
6. Внешнее согласование.
7. Архив.
8. Админка.

Для каждого wireframe нужно проверить:

- один ли главный рабочий контекст;
- понятен ли главный блокер;
- не слишком ли много равных CTA;
- что скрыто по ролям;
- где раскрываются детали;
- не потерян ли текстовый editor-core;
- нет ли карточек внутри карточек.

## 19. Visual Review Checklist Перед PR

Перед каждым frontend PR:

- открыть экран в браузере;
- проверить desktop и narrow viewport;
- сделать screenshot;
- проверить, что текст не перекрывается;
- проверить, что главный CTA один;
- проверить, что роли не видят лишнее;
- проверить, что русские термины понятны;
- проверить, что редактор не сломан;
- проверить, что нет визуального слоя поверх старого UI;
- проверить, что удален или спрятан старый лишний интерфейс, а не оставлен рядом.

Инструменты:

- Browser / Playwright;
- frontend-design для визуального качества;
- web-design-guidelines для UI/a11y review;
- Codex Security для security hardening перед production.

## 20. Implementation Guardrails

Implementation plan нельзя писать, пока не утверждены:

- product spec;
- UX/UI design spec;
- базовые wireframes.

Каждый будущий PR должен явно отвечать:

```text
что переиспользуем;
что удаляем;
что перестраиваем;
как проверяем;
какой пользовательский сценарий стал понятнее;
```

Нельзя:

- добавлять новый UI поверх старого без удаления старой конкурирующей структуры;
- смешивать editor-core bugfix и большой UI rewrite;
- смешивать security hardening и visual redesign в одном PR;
- прятать новые workflow-сущности только на frontend без backend source of truth;
- ломать текстовый редактор.

## 21. Рекомендуемый Порядок UX/UI Проектирования

1. Утвердить product spec.
2. Утвердить этот UX/UI spec.
3. Сделать browser wireframes для главного реестра.
4. Сделать browser wireframes для карточки сюжета.
5. Сделать browser wireframes для текстового workspace.
6. Сделать browser wireframes для production и согласования.
7. Провести role walkthrough.
8. После этого писать implementation plan.

## 22. Open Questions

Перед wireframes нужно уточнить:

1. Нужна ли отдельная колонка `Срок` в реестре как постоянная.
2. Как визуально группировать параллельные треки в одной строке реестра.
3. Нужен ли split-view `реестр + selected details` на desktop или открытие карточки отдельной страницей.
4. Какой уровень мобильной поддержки считать достаточным для MVP.
5. Нужно ли делать Figma-файл или достаточно browser wireframes перед реализацией.
