## Последовательность CP6 после отдельной команды владельца

1. Оставить текущий TTL без изменений. Непосредственно перед окном проверить
   A-записи и TTL на обоих authoritative NS. Назначить окно с учётом того,
   что после смены DNS старый домашний IP может использоваться до 24 часов.
   Всё это время прежний сервис должен оставаться без возможности записи;
   клиент со старым DNS может получить страницу обслуживания или ошибку
   подключения. Это принято для нынешнего периода без пользователей.
2. Перед окном заново сверить точный SHA релиза, сертификат, свободное место,
   здоровье обоих серверов и уже доставленную домой проверенную полную копию.
   Зафиксировать время остановки записи. Остановить домашний backend (и при
   отсутствии проверенного maintenance-режима — gateway), проверить, что
   попытка записи по старому IP не проходит. Сохранить старую БД и весь
   домашний runtime для восстановления. Compose `read_only` защищает только
   файловую систему контейнера и не считается блокировкой записи в БД.
3. На домашнем сервере создать новую зашифрованную полную точку после freeze,
   проверить хеш/расшифровку локально. Снять финальный `pg_dump -Fc`, сохранить
   ciphertext дома, сверить fingerprint до/после дампа. Передать только
   plaintext staging по pinned SSH в root-only каталог VDS; age identity
   остаётся дома. Восстановить в новый пустой production volume, сверить все
   21 таблицу до миграции и Alembic после. Удалить plaintext staging.
4. Запустить VDS только на loopback в maintenance и проверить ответ 503 для
   приложения. Не открывая публичных портов, временно выключить maintenance,
   провести закрытый HTTPS smoke восстановленной рабочей БД без `--write-test`
   и без создания пробного пользователя или сюжета. Проверка создания и
   сохранения уже выполнена на отдельной синтетической БД; её данные удалены.
   Снова включить maintenance и проверить 503. Вручную создать на VDS новую
   зашифрованную точку БД и полный комплект уже восстановленного runtime;
   вручную доставить оба домой и проверить их там до открытия сайта.
5. Привязать gateway к 80/443 с maintenance, проверить TLS, заголовки и
   маршруты извне по прямому IP/`--resolve`. При включённом maintenance
   изменить A-записи `@` и `www` и проверить оба NS. Затем выключить
   maintenance, открыть приложение и сразу проверить HTTPS, вход и сохранение
   с `--resolve` на IP VDS, затем обычное разрешение DNS, внешний браузер и
   установленный CaptionPanels. В этот короткий промежуток
   домен может отдавать 503; сервисом пока никто не пользуется. После первой
   контрольной записи
   на VDS создать и проверить дома внеочередную точку БД до завершения окна.
   Через 24 часа после подтверждённой смены обеих A-записей повторно проверить
   DNS, убедиться, что домашний backend остановлен, и завершить обслуживание
   старого приложения. При наличии работающего maintenance gateway проверить
   его журнал обращений; клиенты с
   устаревшим DNS по-прежнему не должны получать доступ к записи.
6. До первых изменений прикладных данных на VDS при сбое сначала остановить
   запись на VDS (backend и при необходимости gateway), проверить, что попытка
   записи через новый IP не проходит. Затем вернуть прежние A-записи, сверить
   целостность домашней БД и вновь запустить остановленные домашние backend,
   frontend и gateway; проверить вход и запись на прежней площадке. Оставить
   VDS без возможности записи минимум на прежний максимальный TTL после
   подтверждения обратной смены DNS, затем вывести его из обслуживания.
   Пробные сюжеты и пользователи на рабочем VDS до этого рубежа не создаются.
   После первых изменений прикладных данных на VDS откат к старой домашней БД
   запрещён без переноса новых данных; при аварии VDS
   использовать самую свежую проверенную копию VDS и учитывать возможный
   интервал потери данных. CP7 включает подтверждение регулярной доставки DB
   points домой, restore первой новой
   копии, Certbot renewal и мониторинг.
