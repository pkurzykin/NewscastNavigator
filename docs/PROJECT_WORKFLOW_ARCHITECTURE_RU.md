# Архитектура проектной карточки и newsroom-workflow

Дата: 2026-05-06
Статус: active source of truth для product/workflow решений

## 1. Зачем нужен этот документ

Этот документ фиксирует реальный минимальный workflow производства одного новостного сюжета и переводит его в архитектурную модель `NewscastNavigator`.

Он нужен, чтобы:

- перестать обсуждать проект как абстрактный "редактор текста";
- зафиксировать, что такое один `Project` в продуктовых терминах;
- определить, что считается текущим текстом и как это видно всем участникам;
- разложить дальнейший backlog по понятным этапам;
- синхронизировать продуктовые решения, backend, frontend и интеграцию с `CaptionPanels`.

## 2. Короткий вывод

`NewscastNavigator` должен развиваться как единая карточка сюжета, а не как изолированный экран `EDITOR`.

Ключевая сущность:

- один `Project` = один сюжет до выхода в эфир и последующего архива.

Ключевая инвариантная договоренность:

- в системе всегда должно быть явно видно, какое состояние текста является текущим;
- должно быть видно, кто назначил это состояние текущим;
- должно быть видно, кем и когда текст проверен;
- должно быть видно, кем и когда текст вычитан;
- дизайнер и downstream flows не должны опираться на "какой-то последний текст", а только на явное текущее состояние текста;
- если текст изменился после того, как дизайнер начал титрование, система обязана сообщить об этом и дать возможность посмотреть, что изменилось.

### 2.1 Статус реализации на 2026-05-06

К этому дню в web-контуре уже реализованы:

- базовый security baseline: обязательная смена временного пароля, деактивация пользователей, user admin UI, runtime validation конфигурации;
- карточка проекта как единая сущность workflow: метаданные, участники, история, архив/восстановление;
- `source of truth` по тексту: `text_seq`, `current`, `checked`, `proofread`, diff состояния;
- треки `titles/edit/voiceover/final_review` и handoff-сигналы рассинхронизации текста;
- комментарии и action comments с назначением, взятием в работу, закрытием/переоткрытием, привязкой к `text_seq` и текущей `revision`;
- project workspace-функции: material links, project files (upload/download), заметки;
- revisions workflow: baseline, branch/merge, submit/approve/reject, restore-to-workspace, mark-current;
- integration/export контур: Story Exchange, CaptionPanels import/export.

Для текущего web-only release candidate зафиксировано как завершенное:

- UI-redesign карточки и навигации с сохранением editor-core;
- workflow UX по action-comments, персональной очереди и сигналам рассинхронизации текста;
- contract baseline Story Exchange v1 + CaptionPanels integration layer со stable ids;
- frontend tech-pass phase 1 (lazy routes + chunk splitting) без регрессий поведения.

Следующий этап (future roadmap, не блокер текущего RC):

- расширенный workflow правок по видео/титрам/озвучке с более детальной связью "правка -> подтвержденное изменение";
- deep performance validation тяжелых сценариев `Editor` на реальных больших данных;
- расширение integration contracts для будущего `Premiere` adapter поверх versioned Story Exchange.

## 3. Реальный минимальный workflow

Базовый пользовательский сценарий на текущем этапе выглядит так:

1. На медиашаре появляется папка с исходными видеофайлами.
2. Начальник или шеф-редактор ставит задачу на сюжет.
3. Один из текстовых участников начинает писать текст.
4. Текст проверяется и дорабатывается.
5. Корректор вычитывает текст.
6. Диктор начитывает текст.
7. Проект уходит на монтаж.
8. Видео проверяется и при необходимости дорабатывается.
9. Дизайнер делает титры и субтитры через `CaptionPanels`.
10. Готовый результат еще раз отсматривается, возможны правки.
11. Правки "сверху" приходят уже после внутреннего круга проверки.
12. Нужные участники вносят изменения в свои части работы.
13. Готовый сюжет сдается в эфир и архивируется.

Важная особенность этого workflow:

- правки могут возвращаться на любом этапе;
- текст может редактироваться несколькими ролями;
- монтажер может начать по черновому тексту;
- дизайнер должен брать текст только после корректора;
- даже минимальная правка текста после начала титрования должна быть видна дизайнеру.

## 4. Что такое NewscastNavigator в целевой модели

### 4.1 Что система должна делать

`NewscastNavigator` должен быть:

- master-системой по карточке сюжета;
- master-системой по тексту и его рабочему состоянию;
- единым местом для статусов, комментариев, истории и handoff'ов;
- upstream-источником данных для `CaptionPanels` и будущих downstream consumers.

### 4.2 Чем система не должна становиться на первом этапе

На первом этапе `NewscastNavigator` не должен превращаться в полноценный media-archive или DAM/MAM.

Практический вывод:

- тяжелые видео- и аудиофайлы не нужно переносить внутрь системы;
- система хранит ссылки, привязки и типизированные пути к внешним папкам на сетевом шаре;
- бизнес-процесс и source of truth по проекту живут в web-приложении, сами медиа остаются во внешнем storage.

## 5. Модель карточки проекта

Каждая карточка проекта должна объединять всю "жизнь" одного сюжета.

Минимальный состав карточки:

- метаданные проекта;
- участники проекта и их роли;
- ссылки на рабочие папки и материалы;
- живой текст;
- текущее согласованное состояние текста;
- статусы производственных треков;
- комментарии и замечания;
- журнал событий.

### 5.1 Метаданные проекта

Минимальные проектные поля:

- название сюжета;
- рубрика;
- плановый хронометраж;
- общий статус проекта;
- дата создания;
- дата/факт архивации;
- заметка по проекту.

### 5.2 Участники проекта

Участники должны быть реальными пользователями системы под своими учетными записями.

Минимальные ролевые зоны:

- начальник;
- шеф-редактор;
- корреспондент;
- корректор;
- монтажер;
- дизайнер;
- при необходимости отдельные административные роли.

Важно:

- текст может писать и править не только корреспондент;
- в реальном процессе автором текста могут быть начальник, шеф-редактор и корректор;
- поэтому система не должна предполагать единственного "автора" текста.

Ролевое разделение в продуктовой логике должно описывать не "кто единственный владелец текста", а "кто на что имеет право".

Дополнительная практическая договоренность для карточки проекта:

- у текста есть назначаемый автор/ответственный;
- у корректуры есть назначаемый корректор;
- у монтажа есть отдельный назначаемый ответственный;
- у титров есть отдельный назначаемый ответственный;
- эти назначения нужны не только для справки, но и для формирования блока "что ждет меня".

### 5.3 Ссылки на материалы

Внутри карточки нужны не сами медиа, а типизированные ссылки на рабочие папки.

Минимально нужны такие группы:

- исходники;
- озвучка диктора;
- мастер или актуальная видеоверсия;
- при необходимости рабочая текстовая папка;
- дополнительные материалы.

Для каждой ссылки полезны:

- тип;
- путь на сетевом шаре;
- комментарий;
- кто добавил;
- когда добавил.

Практическое уточнение первого этапа:

- система должна уметь привязывать не только папку, но и отдельный файл;
- на первом этапе это именно привязка ссылки или пути, а не загрузка медиа внутрь web-приложения;
- карточка должна явно различать, что привязано: папка с исходниками, папка диктора, мастер-файл, мастер-папка, текстовая папка, дополнительный файл или референс;
- добавление и изменение таких ссылок должно попадать в историю проекта;
- на переходном этапе достаточно хранить нормализованный путь и комментарий пользователя, без сложного файлового менеджера.

Минимальные типы привязок на первом этапе:

- `source_folder`
- `voiceover_folder`
- `master_file`
- `master_folder`
- `text_folder`
- `reference_file`
- `reference_folder`
- `other`

## 6. Модель текста

Это главный продуктовый инвариант проекта.

### 6.1 Два разных состояния текста

В системе нужно четко разделять:

1. `workspace text`
- живой редактируемый текст;
- может меняться часто;
- может редактироваться несколькими ролями.

2. `current text state`
- одно явно отмеченное текущее состояние текста;
- служит основой для handoff'ов;
- должно быть безопасной точкой для downstream-этапов.

### 6.2 Внутренний идентификатор состояния текста

Даже если пользователю не показывать отдельную "новую версию" на каждую запятую, системе нужен внутренний идентификатор состояния текста.

Рабочее название:

- `text_seq`.

Требования:

- увеличивается на каждое осмысленное сохранение текста;
- позволяет понять, на каком состоянии текста выполнена проверка;
- позволяет понять, на каком состоянии текста выполнена вычитка;
- позволяет понять, на каком состоянии текста дизайнер начал титрование;
- позволяет определить, что текст изменился после титрования или после проверки.

### 6.3 Что считается текущим текстом

В системе должен существовать один явный указатель:

- `current_text_seq`.

Он означает:

- именно это состояние текста сейчас считается текущим;
- именно его нужно показывать как рабочую точку согласования;
- именно по нему downstream-этапы понимают, какой текст считается актуальным.

### 6.4 Кто может менять текст и назначать текущее состояние

На текущем этапе зафиксирована такая договоренность:

- начальник, шеф-редактор, корреспондент и корректор могут редактировать текст;
- те же роли могут назначать текущее состояние текста;
- система обязана показывать, кто именно изменил текст и кто именно назначил текущее состояние.

### 6.5 Проверка и вычитка

Нужно различать:

- `checked`;
- `proofread`.

Правила:

- `checked` могут ставить начальник, шеф-редактор и корректор;
- `proofread` может ставить только корректор;
- обе отметки должны быть привязаны к конкретному `text_seq`, а не к проекту "вообще";
- UI должен показывать, кем и когда поставлена каждая отметка.

### 6.6 Устаревание отметок

Если после `checked` или `proofread` текст изменился хотя бы минимально:

- система должна считать, что отметка относится к старому `text_seq`;
- в UI должно быть видно, что текущий текст новее последней проверки или вычитки;
- `proofread` не должен молча считаться действительным для нового текста.

Это особенно важно для дизайнера и для финального производственного контроля.

### 6.7 Одновременное редактирование

На первом этапе не требуется полноценный realtime collaborative editor уровня Google Docs.

Достаточно более прагматичной модели:

- несколько пользователей могут одновременно открыть проект;
- система сохраняет историю, кто и когда сохранял текст;
- при конфликте по более новому `text_seq` пользователь получает предупреждение и возможность посмотреть, что изменилось;
- нельзя строить UX, который молча теряет чужие изменения.

Рабочая модель:

- optimistic concurrency;
- event log;
- diff по изменению текста;
- явный индикатор "появились более новые изменения".

## 7. Проверка, монтаж, титры и downstream-этапы

### 7.1 Монтаж

Монтажер может стартовать по черновому тексту.

Но это не отменяет необходимости фиксировать:

- по какому состоянию текста началась работа;
- изменился ли текст после этого.

Практическое уточнение:

- у трека монтажа должен быть отдельный `edit assignee`;
- если `current_text_seq` изменился после синхронизации монтажа, назначенный монтажер должен видеть явный сигнал и иметь быстрый вход в diff по handoff-тексту.
- правки по монтажу после отсмотра видео должны фиксироваться обычным проектным комментарием с понятным текстом задачи, например с таймкодом и формулировкой изменения.

### 7.2 Титры и дизайнер

Для дизайнера действует более строгое правило:

- дизайнер должен брать текст только после корректора;
- то есть основой для титрования должен быть `current_text_seq`, который имеет актуальную отметку `proofread`.

Если после старта титрования текст изменился:

- система должна показать дизайнеру сообщение вида "текст изменился";
- дизайнер должен иметь возможность открыть текст и посмотреть, что именно изменилось;
- статус титров должен явно показывать, что титры основаны на старом тексте.

Практическое уточнение:

- у трека титров должен быть отдельный `titles assignee`;
- для назначенного дизайнера на главной странице должен появляться явный сигнал "титры требуют пересинхронизации", если после титрования изменился текст.

### 7.3 CaptionPanels

Интеграция с `CaptionPanels` должна подчиняться тем же правилам.

Практический вывод:

- downstream export для титрования должен опираться не на "последний попавшийся workspace", а на явное текущее состояние текста;
- на целевом этапе `CaptionPanels` должен видеть, какой текст является текущим и вычитанным;
- при смене текста после титрования должен быть понятный сигнал о рассинхронизации.

### 7.4 Как фиксируются правки в работе

На ближайшем этапе не нужен отдельный сложный engine для задач и review-объектов.

Базовая рабочая модель должна быть такой:

- замечание, просьба или правка добавляется в проект обычным комментарием;
- комментарий пишет тот, кто ставит правку: начальник, шеф-редактор, корректор или другой участник с правом работы в проекте;
- комментарий должен уметь хранить цель по треку: `general`, `text`, `edit`, `titles`, `voiceover`, `final_review`, `materials`;
- комментарий может быть либо обычной заметкой, либо правкой с признаком `requires action`;
- правка-комментарий должна иметь состояние `open / resolved`;
- комментарий должен быть достаточно конкретным, чтобы по нему можно было взять работу в исполнение;
- для правки желательно хранить привязку к текстовому снимку на момент постановки и на момент закрытия: например `workspace #7`, `current #6`, `proofread #6`;
- если в проекте уже используются сохраненные `revision`, правка должна по возможности помнить и текущую `revision` на момент постановки и закрытия;
- если правка относится к монтажу, в комментарии желательно указывать таймкод или участок видео;
- если правка относится к тексту или титрам, комментарий должен явно указывать, что именно нужно поменять;
- после внесения правки соответствующий участник либо пишет ответный комментарий, либо закрывает правку, либо изменения становятся видны в истории проекта.
- главная страница должна уметь собирать такие комментарии и статусы треков в быстрые очереди вида "ждет меня", "есть правки", "текст", "монтаж", "титры", "озвучка", чтобы сотрудник не искал нужный проект по общему списку.
- внутри карточки проекта комментарии тоже должны собираться по трекам, показывать связанные события истории и, где возможно, давать быстрый вход в diff текста, чтобы исполнитель сразу видел не только саму правку, но и факт внесенных изменений.

Примеры таких комментариев:

- "Монтаж: 00:00:18-00:00:24 заменить кадры на общий план площади"
- "Текст: во втором абзаце убрать фразу про предварительные данные"
- "Титры: поправить должность спикера в СНХ 2"
- "Озвучка: перечитать финальную подводку после правки текста"

## 8. Статусы и треки

Одного линейного project-status для реального workflow недостаточно.

Нужна модель:

- один проект;
- несколько рабочих треков внутри него.

### 8.1 Что уже есть в текущем коде

Сейчас в проекте уже используется более простая верхнеуровневая модель статусов проекта:

- `draft`
- `reviewed`
- `in_editing`
- `in_proofreading`
- `ready`
- `delivered`
- `archived`

Эта модель остается рабочей как текущая implementation baseline, но не покрывает всю реальную производственную картину.

### 8.2 Целевая модель треков

На следующем этапе архитектура должна двигаться к нескольким независимым статусным трекам.

Минимально:

- `project_status`
- `text_status`
- `voiceover_status`
- `edit_status`
- `titles_status`

Дополнительно к статусам треков в продуктовой модели уже нужны:

- `author_user_id`
- `proofreader_user_id`
- `edit_assignee_user_id`
- `titles_assignee_user_id`

Именно эта связка "статус трека + ответственный по треку + признак рассинхронизации" позволяет построить рабочий inbox вида "что ждет меня".

Черновой пример целевых значений:

`project_status`
- `new`
- `in_progress`
- `final_review`
- `ready_for_air`
- `archived`

`text_status`
- `draft`
- `current_set`
- `checked`
- `proofread`

`voiceover_status`
- `not_started`
- `recorded`
- `updated_after_text_change`

`edit_status`
- `not_started`
- `in_progress`
- `review`
- `changes_requested`
- `done`

`titles_status`
- `not_started`
- `in_progress`
- `review`
- `changes_requested`
- `done`
- `outdated_source_text`

Важно:

- это целевая продуктовая модель;
- внедрять ее нужно поэтапно и без разрушения текущего рабочего контура;
- на переходном этапе текущий `projects.status` может оставаться верхнеуровневым summary-статусом.

## 9. История событий

Проект должен давать ответ на вопрос:

- кто, что, когда и почему изменил.

Журнал событий является обязательной частью карточки проекта.

Минимальный набор событий:

- проект создан;
- участник назначен или снят;
- добавлена ссылка на материалы;
- ссылка на материалы изменена или удалена;
- текст изменен;
- текущее состояние текста назначено;
- текст проверен;
- текст вычитан;
- монтаж начат;
- титрование начато;
- текст изменился после начала титрования;
- добавлен комментарий;
- внесена правка после комментария;
- проект отправлен в архив;
- проект восстановлен из архива.

История должна быть пригодна не только для аудита, но и для повседневной совместной работы.

## 10. Комментарии и контур правок

На текущем этапе правки любого происхождения не нужно превращать в отдельный сложный workflow engine.

Это относится и к:

- внутренним правкам от начальника и шеф-редактора;
- замечаниям корректора;
- правкам после отсмотра смонтированного видео;
- замечаниям по титрам;
- комментариям, которые пришли уже после отправки наверх.

Достаточно зафиксировать такую модель:

- правка добавляется в проект как комментарий;
- если это рабочая правка, комментарий помечается как `requires action`;
- комментарий относится к конкретному треку работы;
- комментарий попадает в историю;
- участники проекта видят, что в проекте появились новые замечания;
- соответствующая роль берет правку в работу;
- после выполнения правка переводится в состояние `resolved`;
- факт внесения изменения становится виден либо по истории действий, либо по ответному комментарию.

Важно:

- это не только про текст;
- тот же механизм должен работать для монтажа, титров, озвучки и общих проектных замечаний;
- отдельный специальный объект "внешняя правка сверху" пока не нужен.

## 11. Безопасность и production hardening

Это отдельный приоритет `P0`.

Причина:

- production-сервер не должен оставаться публично доступным с простыми тестовыми учетными данными.

Минимальные обязательные действия:

1. Убрать demo/default учетные записи из production runtime.
2. Сменить пароль `admin` и любые слабые пароли.
3. Повернуть `SECRET_KEY` или `SESSION_SECRET`.
4. Не держать production-приложение напрямую публичным на внешнем `:80` без дополнительной защиты.
5. Свести внешний доступ к reverse proxy, VPN или другой контролируемой точке входа.
6. Ограничить `CORS_ORIGINS` только реальными origin'ами.
7. Добавить управляемые реальные учетные записи под рабочие роли.

Следующий слой hardening:

- смена пароля пользователем;
- деактивация учетных записей;
- UI-управление пользователями, включая создание реальных учеток и сброс временных паролей;
- аудит логинов и действий администрирования;
- базовый rate limiting;
- более строгая session/cookie model, если потребуется.

Любые новые продуктовые задачи должны учитывать, что security-hardening уже не является "необязательным хвостом".

## 12. Статус этапов и ближайший backlog

### Этап P0 — безопасность и доступ

Статус: `в основном завершен`.

- внедрен production-safe auth baseline и запрет unsafe runtime-конфигурации;
- включены обязательная смена временного пароля, деактивация пользователей и админ-операции через UI;
- внешний контур доступа и TLS-hardening остаются отдельным операционным шагом перед публичным rollout.

### Этап P1 — product foundation карточки сюжета

Статус: `завершен`.

- карточка проекта зафиксирована как единая workflow-сущность;
- добавлены участники, назначения и проектные metadata;
- реализованы типизированные material links и рабочая история событий.

### Этап P2 — source of truth по тексту

Статус: `завершен`.

- реализованы `text_seq`, `current`, `checked`, `proofread` с привязкой к состоянию текста;
- добавлено определение устаревания проверок после текстовых изменений;
- доступен diff между текущим состоянием и зафиксированными текстовыми точками.

### Этап P3 — track statuses и handoff

Статус: `завершен`.

- выделены треки `titles`, `edit`, `voiceover`, `final_review`;
- фиксируется привязка треков к актуальному текстовому состоянию;
- в UI/API присутствуют сигналы рассинхронизации при изменении текста после handoff.

### Этап P4 — комментарии, правки и личный inbox

Статус: `завершен`.

- внедрены action comments с assignee, статусом и жизненным циклом;
- добавлены фокусные сигналы MAIN и очереди "что ждет меня";
- сохранены привязки комментариев к `text_seq` и текущей `revision`;
- в карточке комментария есть явный сигнал "текст изменился после постановки" и быстрый переход к diff.

### Этап P5 — CaptionPanels-aware workflow

Статус: `завершен для текущего RC`.

- экспорт и импорт для CaptionPanels реализованы;
- дизайнер получает сигналы рассинхронизации текста;
- в UI присутствуют быстрые переходы к diff для пересинхронизации после изменения текста.

### Этап P6 — администрирование пользователей и production hardening

Статус: `в основном завершен`.

- user admin UI и password lifecycle реализованы;
- остаются операционные задачи: финальный rollout реальных учетных записей, домен/TLS и внешний perimeter hardening;
- эти задачи считаются отдельным deploy-stage блоком перед публичным rollout.

### Этап P7 — следующие продуктовые шаги

Статус: `future roadmap (после текущего RC)`.

- довести единый workflow постановки и отработки правок по видео/титрам/озвучке;
- стабилизировать интеграционный контракт перед расширением в сторону Premiere plugin;
- провести frontend tech-pass (chunk splitting и точечная оптимизация тяжелых экранов).

## 13. Открытые вопросы

На момент фиксации этого документа остаются открытыми, но не блокирующими следующие вопросы:

- какой UX выбрать для конфликтов параллельного редактирования одного текста;
- нужен ли отдельный "подробный diff режим" (word-level) поверх текущего snapshot-diff;
- когда расширять текущий role model под дополнительные newsroom-роли без усложнения permission-модели.

## 14. Как использовать этот документ дальше

При обсуждении новых задач исходить из следующих правил:

- начинать не с экранов, а с инвариантов карточки проекта;
- любые изменения текста рассматривать через призму `current_text_seq`, `checked`, `proofread`;
- любые решения для дизайнера и `CaptionPanels` проверять на вопрос "что произойдет, если текст изменится после старта титрования";
- не раздувать систему до media-storage без прямой необходимости;
- приоритизировать безопасность production рядом с продуктовой архитектурой, а не после нее.
