# Web Smoke Checklist

Дата актуализации: 2026-05-07

## Зачем нужен этот документ
Это короткий ручной чек-лист для подтверждения, что новый web-контур реально работает как основная версия проекта.

Использовать его:
- локально после заметных изменений в `backend/` или `frontend/`;
- перед первым аккуратным обновлением домашнего сервера;
- после изменений в правах, workflow, архиве, экспорте или работе с файлами.

Важно:
- сначала прогоняем локально;
- сервер не трогаем, пока не проведен отдельный аудит того, что уже работает на домашнем сервере.

## Минимальные предусловия
- backend поднят;
- frontend поднят;
- доступна тестовая БД;
- включен demo seed или есть тестовые данные.

Demo-пользователи по умолчанию:
- `admin / admin123`
- `editor / editor123`
- `author / author123`
- `proofreader / proof123`

Важно: это только локальный smoke-набор. Для production demo-пользователи и default credentials запрещены: использовать реальные учетные записи, временные пароли с обязательной сменой и hardening-профиль из `docs/DEPLOYMENT_UBUNTU_RU.md`.

## Чек-лист

### 1. Логин и базовый запуск
- Зайти под `admin`.
- Убедиться, что открывается `MAIN`, список проектов загружается, ошибок API нет.
- Перелогиниться под `editor`, `author`, `proofreader` и убедиться, что вход работает для всех ролей.

### 2. MAIN
- В `MAIN` загрузить список рабочих проектов.
- Проверить фильтры:
  - поиск по названию;
  - статусы;
  - рубрика;
  - участник;
  - дата создания.
- Создать пустой проект.
- Создать копию последнего проекта.
- Создать копию выбранного проекта.
- Открыть созданный проект в `EDITOR`.

### 3. ARCHIVE
- Отправить проект в архив под `admin` или `editor`.
- Переключиться в `ARCHIVE`.
- Проверить фильтры:
  - название;
  - рубрика;
  - кто архивировал;
  - дата архивации.
- Восстановить проект и убедиться, что он возвращается в предыдущий рабочий статус, а не просто в `draft`.

### 4. EDITOR: таблица и workflow
- Открыть рабочий проект.
- Проверить, что в шапке и блоке метаданных видны:
  - статус;
  - источник клона;
  - время последнего изменения статуса;
  - автор;
  - исполнитель;
  - корректор;
  - архивные метаданные для архивного проекта.
- Изменить:
  - название;
  - рубрику;
  - хронометраж;
  - статус;
  - назначения.
- Добавить, удалить и сохранить строки сценария.
- Проверить валидации:
  - неверный `TC IN/TC OUT`;
  - `TC OUT < TC IN`;
  - у `СНХ` заполнены не все обязательные части: `ФИО` и `Должность`.

### 5. Права по ролям
- Под `author`:
  - в статусах кроме `archived` и `in_proofreading` строки должны редактироваться;
  - в `in_proofreading` строки и workspace должны быть заблокированы;
  - архивный проект должен быть полностью read-only.
- Под `proofreader`:
  - в `in_proofreading` строки и workspace должны редактироваться;
  - смена статуса должна быть доступна;
  - вне архива проект не должен быть read-only.
- Под `editor` и `admin`:
  - редактирование должно работать во всех рабочих статусах;
  - архив должен оставаться read-only до восстановления.

### 6. WORKSPACE
- Проверить сохранение:
  - `file_root`;
  - `project_note`.
- Добавить комментарий.
- Удалить свой комментарий.
- Загрузить файл допустимого типа.
- Скачать файл.
- Удалить файл.
- Убедиться, что после загрузки файла в истории появляется событие `file_uploaded`.

### 7. История проекта
- Открыть блок истории.
- Убедиться, что видны минимум такие события:
  - `project_created`;
  - `project_cloned`, если проект был создан копированием;
  - `status_changed`;
  - `project_archived`;
  - `project_restored`;
  - `file_uploaded`, если загружался файл.

### 8. Экспорт
- Сформировать `DOCX`.
- Сформировать `PDF`.
- Убедиться, что в экспорте корректно подтягиваются:
  - название;
  - рубрика;
  - автор;
  - исполнитель;
  - корректор;
  - строки сценария.

### 9. Action comments и рассинхронизация текста
- Под `editor` в `EDITOR` поставить action-комментарий по треку `titles` или `edit`.
- Зафиксировать `text_seq`, на котором комментарий поставлен.
- Изменить текст так, чтобы `text_seq` вырос.
- Убедиться, что в карточке action-комментария появился сигнал:
  - «Текст изменился после постановки задачи: #N -> #M».
- Нажать кнопку diff в карточке комментария и проверить, что сравнение открывается без ошибки.
- Проверить lifecycle:
  - `1. Взять в работу` -> `Вернуть в Open` -> `3. Закрыть задачу` -> `Переоткрыть задачу`.
- Убедиться, что история проекта фиксирует переходы статусов action-комментария.

## UI rescue / main queue smoke

- Войти пользователем с ролью `editor`.
- После UI replacement/refactor проверить, что словари статусов, дат и приоритетов очереди не разъехались между `MAIN` и строками очереди.
- Проверить, что `MAIN` показывает один рабочий список `Очередь сюжетов`, без sidebar и вкладочной карточки поверх редактора.
- Проверить, что переключатель списка, поиск, быстрые фильтры и действия выбранного сюжета собраны в один верхний блок управления очередью.
- Переключить `Основной список` / `Архив`.
- Проверить быстрые фильтры `Весь MAIN`, `Ждет меня`, `Мои action-задачи`, `Есть правки`, `Текст`, `Монтаж`, `Титры`, `Озвучка`.
- Проверить, что в `MAIN` первыми поднимаются строки с приоритетом `Срочно`: назначенные action-задачи, устаревший `current`, рассинхронизация монтажа/титров/озвучки.
- Проверить поиск и блок `Расширенные фильтры`.
- Проверить, что строка очереди явно показывает handoff `workspace/current/proofread`, производственные треки, команду и последнюю активность без отдельной карточки сюжета.
- Проверить узкую ширину экрана: верхний блок управления складывается вертикально, быстрые фильтры прокручиваются горизонтально, таблица очереди не ломает текст кнопок.
- Выбрать строку через `Выбрать` и убедиться, что верхняя панель действий показывает выбранный сюжет.
- Открыть редактор через `Открыть` в строке и через `Открыть редактор` в панели действий.
- Проверить, что редактор открывается напрямую, без project-card wrapper и без размонтирования через вкладки.
- Проверить верх редактора: `Workspace text`, `Current handoff`, `Proofread` отображаются как единая полоса handoff-состояний, без дополнительных вкладок и wrapper вокруг editor-core.
- Проверить переключатель `Редактирование` / `Проверка`: он отображается как единый режимный блок редактора, а не как отдельная вкладочная карточка.
- Проверить блок `Состояние текста`: `Workspace`, `Current handoff`, `Checked`, `Proofread` читаются как последовательность состояний текста, а кнопки handoff не меняют фокус editor-core.
- Проверить создание сюжета, копирование из последнего, копирование из выбранного, архивирование и восстановление.
- Проверить, что в очереди видны признаки `workspace/current/proofread` и сигналы рассинхронизации монтажа, титров и озвучки.

## Production perimeter smoke

Выполнять после server deploy и до публичного rollout или сразу после включения публичного bind.

### 1. Env и compose
- Проверить, что production `.env` не содержит `change-this-*`.
- Проверить, что `ENVIRONMENT=production`.
- Проверить, что `SEED_DEMO_DATA=false`.
- Проверить, что `DATABASE_URL` указывает на PostgreSQL, а не SQLite.
- Проверить, что `CORS_ORIGINS` содержит только реальные `https://` origins и, если нужен CaptionPanels, `null`.
- Проверить, что `NGINX_BIND_HOST=127.0.0.1` до финального открытия наружу или `0.0.0.0` только после DNS/TLS/access policy.
- Выполнить `docker compose --env-file .env -f compose.yaml config`.

### 2. Reverse proxy и TLS
- Проверить, что `http://<domain>/` возвращает redirect на `https://<domain>/`.
- Проверить, что `https://<domain>/api/health` отвечает успешно.
- Проверить, что TLS certificate покрывает основной домен и `www`, если `www` используется.
- Проверить security headers: `Strict-Transport-Security`, `X-Content-Type-Options`, `Content-Security-Policy`.
- Проверить, что backend и frontend контейнеры не публикуют host-порты напрямую.

### 3. Production accounts
- Войти под реальным admin account.
- Убедиться, что первый вход с временным паролем требует смены пароля.
- Проверить, что `admin/admin123`, `editor/editor123`, `author/author123`, `proofreader/proof123` не дают доступ.
- Проверить в admin UI, что demo-users отсутствуют, деактивированы или заменены реальными сотрудниками.
- Создать одного реального пользователя через admin UI, сбросить временный пароль, убедиться в обязательной смене.

### 4. Production workflow smoke
- Открыть список сюжетов под реальным пользователем.
- Создать тестовую карточку сюжета без demo seed.
- Назначить автора/исполнителя/корректора из реальных users.
- Изменить текст, назначить текущий текст, отметить проверку и вычитку.
- Проверить экспорт и CaptionPanels/Story Exchange smoke, если этот rollout включает downstream flow.
- Архивировать тестовую карточку или удалить тестовые данные согласно операционной политике проекта.

## Что считать стоп-фактором
- backend или frontend не поднимается;
- `MAIN` или `ARCHIVE` не загружаются;
- `EDITOR` получает неполные метаданные проекта;
- роли дают доступ не тем пользователям;
- архивный проект редактируется;
- restore не возвращает проект в предыдущий статус;
- экспорт не формируется;
- файлы загружаются, но история проекта не пополняется;
- action-комментарий не показывает рассинхронизацию после изменения текста или не открывает diff.

## Что делать после smoke-check
- если локально все прошло, можно переходить к production/deploy-подготовке;
- если найдены баги, сначала закрыть их локально;
- перед работой с домашним сервером отдельно зафиксировать:
  - как там сейчас запущен проект;
  - где лежат данные;
  - какие контейнеры, volumes, compose-файлы и reverse proxy уже используются.
- перед публичным rollout обязательно пройти `Production perimeter smoke`.
