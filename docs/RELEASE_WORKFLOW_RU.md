# Выпуск NewscastNavigator

Отдельная ветка → проверки → домашняя приёмка → согласование владельцем →
выпуск того же кандидата на VDS → проверка результата. Этот документ задаёт
порядок; сам по себе он не разрешает внешние действия.

## 1. Подготовка изменения

- Проверить Git и [текущий контекст](PROJECT_STATE_RU.md), получить утверждение
  плана по файлам, реализовать в отдельной ветке/worktree.
- Для изменённого поведения сначала тест, затем реализация; проверки
  выбираются по [инженерным правилам](ENGINEERING_PLAN_RU.md) и риску.
- Существенное изменение получает независимое ревью и отдельную верификацию
  одного снимка. После исправлений затронутые проверки повторяются.
- Кандидат фиксируется полным SHA. Изменение кода/конфигурации/миграций после
  проверки создаёт новый кандидат и требует соответствующей проверки.

## 2. Домашняя приёмка

По разрешению на домашнее обновление координатор применяет
[канонический updater](HOME_TEST_WORKFLOW_RU.md) к точному SHA. До применения:
preflight, исходный healthy-стек, место, копия и материалы возврата.
Тестовая БД остаётся отдельной и синтетической.

Проверить установленный SHA/image IDs, health, пользовательские сценарии,
сохранность media/SMB и доступ только LAN. При изменении сценария — сохранение
и повторное открытие; DOCX/CaptionPanels включаются при изменении их контрактов
или как релевантный smoke релиза. Сборка/API-ответ не заменяют UI-проверку.
Владелец принимает результат; замечания относятся к конкретному кандидату.

## 3. Карточка production-кандидата

Куратор релиза собирает карточку до запроса разрешения. Значения заполняются
свежими доказательствами. Прошлый зелёный CI не доказывает новый кандидат.

```text
Версия / полный candidate SHA:
Ветка и ожидаемый результат интеграции:
Состав изменения и затронутые данные:
Проверки / CI (если публикация разрешена), привязка к SHA:
Независимые review и verification, снимок:
Домашний installed SHA / image IDs / фактическая приёмка:
Способ поставки / результаты RELEASE_LICENSE_CHECKLIST_RU.md:
Миграции: исходная и целевая схема, совместимость приложения:
Копия до deploy: ID, время, целостность, путь восстановления:
Rollback: образы/исходники, совместимость схемы, условия остановки:
Проверки после выпуска и ответственный:
Ограничения / нерешённые риски:
Запрошенные внешние действия (push/PR/merge/tag/release/deploy отдельно):
Решение владельца, точный кандидат и разрешённые действия:
```

Если интеграция меняет SHA, полученный commit становится новым кандидатом:
проверить diff, CI и домашнюю установку итогового SHA. Номер версии и имя
ветки не заменяют привязку к commit и образам. Отсутствующее доказательство
отмечается `NOT_RUN/UNKNOWN` с объяснением, а не PASS.
Проверка состава фактически поставляемых компонентов выполняется по
[RELEASE_LICENSE_CHECKLIST_RU.md](RELEASE_LICENSE_CHECKLIST_RU.md); реестр
зависимостей сам по себе не подтверждает весь комплект поставки.

## 4. Выпуск на VDS

Владелец явно разрешает конкретные внешние действия для кандидата.
Push/PR/merge не подразумевают tag, публикацию или deploy; разрешение этапа
действует в своих границах. Выполняет координатор/назначенный исполнитель.
У куратора релиза режим чтения и проверки, без самостоятельного deploy.

Перед операцией сверить фактический runtime и схему VDS, кандидата,
доступность копии и recovery path из [Hostland](../deploy/hostland/README.md).
Копии/журналы вне Git; секреты передаются закрытым способом. Тестовые записи
не переносятся в production. Пересборку исходной БД из исторического плана
не повторять. При несовместимости схемы, неподтверждённой копии, неожиданном
состоянии или выходе за разрешение остановить выпуск и сообщить препятствие.

## 5. Проверка и откат

После выпуска: installed SHA/image IDs, health, авторизация, сохранение и
повторное открытие безопасного согласованного тестового сюжета, релевантные
DOCX/CaptionPanels smoke, отсутствие новых ошибок и состояние двух мониторов
UptimeRobot. Запись требует разрешённой тестовой учётной записи и согласованного
набора данных; пароли вводит владелец закрытым способом.

Откат выбирается по фактической схеме. Старые образы можно вернуть только
при доказанной совместимости. Если нужен restore БД, определить потерю записей
после копии и получить разрешение на это восстановление. Успех 2E при одинаковой
схеме не доказывает rollback любой миграции. Использовать согласованный runbook,
без `down -v` или удаления текущих данных как универсального восстановления.

Релиз завершён, когда согласованные проверки подтверждены и записаны:
версия/SHA, копия, операция, evidence, ограничения и решение о принятии.
Обновить PROJECT_STATE и журнал. Наблюдение после выпуска назначается отдельно
со сроком и условиями уведомления. Постоянный агент или автоматический deploy
этим процессом не создаётся.
