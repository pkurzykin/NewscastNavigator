2. Прочитать корневой AGENTS и этот файл; определить задачу и действующие
   разрешения из текущего разговора.

   вопроса, а не как инструкции к повторному выполнению.

## Принятый процесс

Код в отдельной ветке/worktree → проверки → точный commit на постоянном
домашнем сервере → приёмка → отдельное согласование выпуска на VDS →
проверка результата. Поднимать backend/frontend на MacBook для обычной
интеграционной проверки не требуется. Быстрые unit/build проверки остаются
доступными; localhost-контур используется по конкретной необходимости.

Первоначальный Product Reset завершён. Требования действуют в `docs/product/`,
старые планы пересборки — история. Рабочая production-БД защищается миграциями
и копиями; разрешения прежнего прототипа на неё не распространяются.

## Открытые вопросы и следующий шаг

- Причина остановки гостевых часов VDS до 04:59 UTC не установлена.
  `makestep 1 3` объясняет отсутствие автоматического большого шага после
  начала сбоя, но не сам откат часов. В поддержку Hostland отправлен запрос
  на расследование гостевых и хостовых причин без перезагрузки/изменений
  без согласования. Следить за часами и копиями как минимум до 29.09;
  почтовый монитор оставлен включённым.
- 28.09 по новому разрешению владельца автоматическая очистка включена на
  VDS и дома: DB не моложе 30 суток, минимум 8 недельных full и все full,
  нужные оставшимся DB. Дома cron ежедневно в 06:11 МСК, отдельный
  forced-command SSH-ключ для удаления, закрытый журнал VDS и почтовый
  сигнал только при сбое. Первый ручной `--apply` завершился успешно,
  `deleted=0`; live dry-run и VDS scan показали ноль кандидатов. Первый
  запуск по cron и фактическое удаление зрелой точки ещё не наблюдались.
  Подробности и границы — в `deploy/hostland/RETENTION_RU.md`.
- Обновления VDS не установлены в этом этапе: среди доступных есть
  `containerd.io`; назначить окно после оценки влияния на production.
- Внешний heartbeat дома отложен владельцем. Два монитора VDS не доказывают
  доступность дома.
- Откат после несовместимой миграции не проверен этапом 2E: потребуется
  отдельный план совместимости/restore с оценкой потери записей.
- 3A завершён локально: активная документация переименована, контекст,
  релизный процесс и три конфигурации ролей подготовлены. Независимые review
  и verification PASS; ограничения проверок записаны в журнале.
- 28.09 эксплуатационный commit `38ac34d` включён fast-forward в локальный
  `main` и опубликован в GitHub. CI этого SHA: backend/operations и frontend
  PASS. Закрывающий документальный checkpoint также опубликован; локальный и
  GitHub `main` синхронизированы. Четыре завершённые ветки удалены после
  проверки их включения в `main`. Старые detached worktree сохранены вместе

  узких ролей отдельно не проверялась.
- Далее — проверить первый cron-запуск 29.09 по status/journal, наблюдать за
